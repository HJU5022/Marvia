# 판정 파인튜닝 1회 성공 토론 (단독 문서)

이 문서 하나만 읽고도 토론에 참여할 수 있게 썼다. 다만 이 문서는 **토론용 요약**이다. 실제 계약과 결과는 버전을 고정한 판정 지시문·스키마·fixture·가격 산식·평가 실행기로 재현한다(라운드 17 E4). 레포를 볼 수 없는 AI 도구(ChatGPT, Gemini 웹 등)도 대상이다.
목표는 하나다: **학습 job을 딱 한 번 만들고, 그 한 번으로 통과시키는 절차**를 두 AI가 번갈아 따져 합의한다.
"1회"는 **OpenAI(또는 대체 플랫폼)에 학습 job을 1개만 생성한다**는 뜻이다. 학습 전 측정·검사를 여러 번 반복하는 것은 1회에 포함되지 않는다.
합의된 절차는 레포의 docs/specs/judge-finetune.md(Spec)에 반영하고, 사람(김승욱, 하정운)이 최종 결정한다.

기준 시점: 2026-09-28, 레포 origin/main 커밋 0a9124e (라운드 10에서 38e302b에서 갱신. #53 Spec, #54 Vertex 경로 머지 포함). 이 문서는 docs/specs/judge-finetune-debate.md(라운드 1~4)를 이어받아 대체한다.

1. 주장마다 근거를 붙인다

## 1. 서비스 요약

Marvia는 부산항으로 해상 수입하는 소량 화주가 B/L 번호와 판매 예정일을 넣으면 "내 화물, 지금 신경 써야 하나?"에 답하는 에이전트다. 판정은 셋이다.

- fine (괜찮음): 판매일 전에 할 일 없음
- watch (지켜볼 것): 여유는 있지만 확인할 것이 있음
- act (지금 조치): 지금 움직이지 않으면 판매일을 놓침
- null (판정 보류): 결정적 정보가 없어서 되묻는다

원칙: 사실 값은 코드가 계산한다. 신호 7종의 상태, 여유 일수(days_margin), 신뢰 ETA는 코드 값이고 LLM이 바꾸면 안 된다. LLM은 그 값을 읽고 해석만 한다.

LLM이 하는 일은 셋뿐이다: 동명 선박 중 고르기(가끔), **2층 판정 judge()(2층까지 온 요청마다)**, 후속 질문 답(가끔). 파인튜닝 대상은 judge() 하나다.

## 2. 요청 한 번의 흐름

```
POST /api/agent
 1. UNI-PASS 통관 조회 (코드가 직접)
 2. 선박 식별 (MRN으로 호출부호 → 없으면 선명 검색, 여럿이면 LLM pick_vessel)
 3. 도구 4종: 선박 후보, 실시간 위치(ShipFinder), 입항 일정(해수부), 남은 거리(searoute)
 4. 1층 신호 7종 계산 (signals.py, 3절)
 5. 여유 일수 = 판매일 - 신뢰 ETA (한국 날짜)
 6. 2층 판정 judge() → 출력 검증 V1~V7 (4절) → 위반이면 재시도, 최대 3회
 7. 응답 (판정, 이유, 상충, 할 일, 답, 통관 해설, 근거 카드)
```

판정 단계의 실제 순서 (발췌 5.2):
- 지원 범위·선박 식별·반출 조기 반환(정운님 로컬 750a93f)을 통과해 2층에 도달한 요청에서 judge()를 호출한다. 신호가 전부 clear여도 호출되고, 그때는 판정만 규칙으로 fine으로 덮고 LLM 답에서는 문장과 통관 해설만 쓴다
- L1(라운드 17): Skill의 fine 조건은 "모든 신호 clear + ETA 근거 2개 이상 일치"인데, 라우터는 일곱 신호가 모두 clear면 ETA 근거 개수를 보지 않고 fine으로 덮는다. all-clear 판정에는 ETA 근거 조건과 D4 결정을 명시적으로 적용해야 한다
- judge()가 JSON 모양이 틀린 답을 내면(파싱 실패) LLMError가 되고, **재시도 없이 status=partial**로 끝난다. V1~V7 위반률에는 잡히지 않는다
- V1~V7 위반이면 위반 내용을 붙여 다시 묻고(2회째), 3회째는 "JSON only, follow every rule"을 덧붙인다. 세 번 모두 위반이면 status=failed
- LLM 호출 자체의 재시도(HTTP 429·502·503)는 chat() 안에서 최대 2회로 별도다

## 3. 신호 7종과 판정 규칙

### 3.1 신호 (코드가 실제로 낼 수 있는 상태)

임계값 원본은 skills/ais-reliability/rules.md: position_stale_hours 6, eta_conflict_hours 12, anchor_speed_kn 0.5, anchor_wait_hours 24, busan_radius_nm 30, margin_act_days 2.

| 신호 | unknown | clear | triggered |
|---|---|---|---|
| position_stale | 위치 없음 | 마지막 수신 ≤ 6시간 | > 6시간 |
| eta_conflict | AIS ETA 또는 해수부 예정이 없음 | 차이 ≤ 12시간 (해수부가 00:00이면 그날 하루를 범위로) | > 12시간 |

| dest_changed | 위치 없음 | 목적지 코드 KRPUS | 그 외 (빈 값, 다른 항구, 깨진 값) |

| customs_hold | 통관 정보 없음 | 단계명에 아래 낱말 없음 | 단계명에 검사·보류·정지·반송·폐기 |
| sales_date_exceeded | 신뢰 ETA 또는 판매일 없음 | days_margin ≥ 0 | days_margin < 0 |

### 3.2 판정 규칙 (skills/ais-reliability/SKILL.md)

| 판정 | 조건 |
|---|---|
| act | anchor_wait, customs_hold, sales_date_exceeded 중 하나라도 triggered. 또는 다른 신호가 triggered이고 days_margin < 2 |
| watch | 위 셋은 clear, 다른 신호가 triggered (Skill 원문). "days_margin ≥ 2"는 원문에 없고, act의 "여유 < 2"가 먼저 적용된다는 데서 A가 유도한 것이다 |
| fine | 모든 신호 clear, ETA 근거 2개 이상 일치 |
| null | 위치가 아예 없는 등 결정적 신호 unknown. 할 일에 포워더 입항 예정일 문의 |

상충 우선순위: 해수부 관제 실적 > 해수부 입항 예정 > AIS ETA > AIS 목적지 문자열. 오래된 위치(stale)는 위치 없음과 다르다. 되묻지 않고 "마지막 수신 위치"로 판정한다.

## 4. 출력과 검증

### 4.1 judge() 출력 (strict json_schema로 강제)

```json
{"verdict": "fine|watch|act|null",
 "reasons": [{"rule": "신호 id", "value": "문자열", "triggered": true}],
 "conflicts": [{"signals": ["..."], "chosen": "근거 출처 이름", "why": "한국어"}],
 "actions": ["한국어 짧은 할 일"],
 "answer": "한국어 2~3문장",
 "customs": {"plain_explanation": "한국어", "next_stage": "단계 이름 또는 null", "needs_broker": false}}
```

### 4.2 검증 7규칙 (validate.py)

| 규칙 | 내용 |
|---|---|
| V1 | 위치가 stale이면 answer에 "현재 위치" 금지 |
| V2 | act·watch면 reasons 1개 이상, rule은 신호 7종 id만 |
| V3 | ETA가 있으면 근거 카드 1장 이상 |
| V4 | 선박 식별 uncertain이면 verdict null |
| V5 | insufficient면 물을 것 1개 이상 |
| V6 | conflicts[].chosen은 근거 카드 source 이름만: shipfinder, mof, searoute, unipass, rule |
| V7 | answer 속 숫자는 근거 카드 값(날짜 포함) 또는 여유 일수에서 온 것만 |

근거 카드(evidence)에는 UNI-PASS 입항일, AIS ETA, 해수부 예정·실적, 거리, 신호 값, 신뢰 ETA, 여유 일수가 들어간다. judge()의 입력에는 해수부 예정·실적, AIS ETA, 신뢰 ETA 날짜가 없다(발췌 5.1). 입력에 있는 날짜는 UNI-PASS의 entry_date와 stage_history[].at(customs를 세 필드만 빼고 통째로 넣기 때문, 라운드 9 GPT Luna 지적), 그리고 calc_eta다. calc_eta는 신뢰 ETA가 아니라 "지금 + 남은 거리 ÷ 현재 속력"으로 계산한 참고값이고(signals.py:149 _calc_eta, 근거리에서 크게 나온다), 근거 카드에는 들어가지 않는다. 그래서 모델은 신뢰 ETA·해수부·AIS 날짜를 볼 수 없고(UNI-PASS 날짜는 본다), calc_eta 날짜를 답에 쓰면 V7에 걸릴 수 있다(근거 카드의 다른 날짜와 숫자 조각이 겹치면 통과할 수도 있다).

## 6. 평가셋 (파인튜닝 성공 여부를 가르는 시험지)

### 6.3 평가 축과 게이트 (PRD 8절)

- 축: verdict_accuracy, act_recall, insufficient_precision, vessel_match_accuracy, customs_explanation(LLM-as-judge, 생성 모델과 다른 회사), grounded(V7 숫자 조각 통과율, 보조 지표. answer의 숫자 조각만 보며 날짜 조각을 섞어도 통과할 수 있고 actions·customs는 보지 않는다. 날짜와 actions·customs는 사람 또는 별도 의미 검사로 확인한다), schema_pass(V1~V7 위반율)
- 비교 구성: (a) 규칙만 (b) 규칙+모델 A (c) 모델 B. 파인튜닝 모델은 여기에 구성 하나를 더한다
- 게이트(하나라도 걸리면 채택 안 함): act 누락 1건 이상, 식별 오확정 1건 이상, 스키마 통과 95% 미만, 주입 오작동 1건 이상, p95·요청당 비용 상한 초과
- PRD 신호 상충 5건(상충 1~5 = B05, B04, B03, B06, B07)에서 4건 이상 맞혀야 LLM 기여를 인정한다(PRD 8절). 기준은 B07(식별 단계, judge() 없음)을 포함한 5건 중 4건이다. judge()만 보면 4건 모두 맞혀야 한다

### 6.4 평가를 돌리는 도구의 상태

- 평가 실행기 evals/run_eval.py(작업 D8)는 **아직 없다**. 담당은 하정운. 파인튜닝 비교는 이게 있어야 가능하다
- 외부 API는 REPLAY_MODE 재생(evals/fixtures/)으로 키 없이 먹일 수 있다. LLM은 실제 호출이다
- 평가셋 1회 실행 비용: 기준 모델은 코드가 아니라 MODEL_A 환경변수가 정한다(llm.py, .env.example 빈 값). gpt-4o-mini 가정 시 판정 24회 약 $0.017(추정). 기준 모델과 FT 모델의 추론 단가는 S1 계산표에서 선택 모델의 공식 가격으로 산출한다. FT 모델이 기준보다 싸다는 보장은 없다(예: gpt-4.1-mini FT는 입력이 줄어도 더 비쌀 수 있다, 가격 재확인 필요). KEEP 비용 조건 충족 여부는 미정이다

## 7. 파인튜닝 계획 요약

- 방식: 증류. 짧은 지시문(약 100토큰)만으로 풀 프롬프트 수준의 판정 JSON을 내도록 학습. 스키마는 추론 때 계속 보낸다(입력 약 950토큰 목표)
- 대상 모델: OpenAI SFT 가이드가 명시한 gpt-4.1-nano-2025-04-14 또는 gpt-4.1-mini-2025-04-14 (11절 24)
- 학습 입력: 코드가 만든 가공 입력. 평가셋 30건과 실제 수집 데이터는 쓰지 않는다
- 조합표 (docs/specs/judge-finetune-cases.md): 신호 하나만 켜짐 48, 전부 clear 20, 둘 이상 28, unknown·보류 20, 통관 해설 16, 울타리·주입 12 = 144건. 값만 바꾼 변형을 붙여 약 290건. 변형은 판정이 뒤집히는 경계 쌍(5.9h/6.1h, 여유 1/2일)으로 만든다
- 목표 분포: act 40%, watch 25%, fine 25%, null 10%. 20%는 검증용으로 뗀다
- 정답 작성: 규칙으로 직접 쓸지, 교사 모델이 쓰고 정책 검사기로 거를지는 사람 결정이다(11절 38). 어느 쪽이든 V1~V7, 정책 검사기, 모순 탐지를 걸고 경계 사례는 사람이 전수 검토한다. "증류"는 교사 모델 방식을 고를 때의 이름이다
- few-shot 사전 측정용 예시 5개는 학습·평가 데이터와 분리한다 (fine 1, watch 1, act 2, null 1)
- 비용 추정: 300건 규모 한 번에 성공 시 $5~8, 현실적으로 $11~19. **검산 전 추정**이고 짧은 입력 950토큰도 목표치다. 선택 모델의 실제 파일 토큰·epoch·공식 가격·교사 생성·평가·재시도를 넣어 S1에서 다시 계산한다(라운드 17 E1)
- 플랫폼 제약: OpenAI 가격 페이지에 "파인튜닝 플랫폼이 신규 사용자에게 닫혔다"는 공지가 있다. 대체 경로는 Vertex AI Gemini 지도 튜닝 (11절 26a~26c, 31)

**이 절차는 학습 실행 절차가 아니라 학습 전 게이트다.** 지금은 실행 단계가 아니다. 실제 순서는 **1단계 사람 결정 → 0단계 구현·테스트 → 2~6단계 검사 → 7단계 학습 1회 → 8단계 평가 캠페인 1회**다(라운드 17). 학습 job은 진행 중단 조건 S0~S3을 모두 통과한 뒤 딱 1번 만든다.

   - **진행 중단 조건 S0**: 0단계 구현이 끝나고 테스트가 통과했다는 기록이 없으면 job을 만들지 않는다. 문서에 계획이 적힌 것은 구현 완료가 아니다(라운드 17). 여기에 **all-clear ETA 계약(11절 36)**을 포함한다: 1단계에서 정한 정책대로 `_judged()` 또는 그 앞의 규칙 분기를 고치고, ETA 일치 근거 0·1·2개와 여유 0·1·2일 조합의 회귀 테스트가 통과한 기록이 없으면 job을 만들지 않는다(라운드 19). 지금 라우터(agent.py:166~169, 0a9124e)는 신호가 전부 clear면 ETA 근거 개수를 보지 않고 fine으로 덮는다. **또 다음 기록 중 하나라도 없으면 job을 만들지 않는다**: (가) 실행기로 판정 호출 문항 수를 실측해 6.2절과 대조한 기록(11절 7i) (나) 3단계 정책 검사기 통과율 100% 기록(13i) (다) 6단계 다섯 용도 문항·fixture·근접 변형 겹침 0건 기록(9i) (라) 8단계 평가 캠페인 설정 파일 저장 기록(17i) (마) 11절 사람 결정 전부의 결정 기록(라운드 21 전 A 자체 점검)
1. 기준 고정 (사람 결정): D1~D9를 Skill 문서·SDD에 확정한다. 30건 기존 라벨은 잠정본이라 확정한 기준으로 사람이 재검수한다(라운드 17 C1). 특히 B08은 D3과 함께 **입력을 바꾸거나(수집 이력 연결) 정답을 바꾼다**. F08은 D9로 경로를 정한 뒤 평가에 다시 포함한다. D5의 unknown 종류와 D6의 여유 null은 보류·판정 조건을 표로 고정한 뒤 N03 등 라벨을 재검수한다(라운드 17 L2). N03 한 건을 일반 규칙으로 삼지 않는다
   - **all-clear ETA 근거 정책 (라운드 19, 11절 3)**: D4의 여유 0~1일과 별도로, 신호가 전부 clear지만 일치하는 ETA 근거가 2개 미만일 때 fine을 금지하고 watch·null·다른 상태 중 무엇으로 처리할지 사람이 정한다
   - 같이 정할 것: (1) job의 **플랫폼과 실패 시 처리**(11절 31) (2) **총 예산 상한과 결정 날짜**(11절 32) (3) **봉인 세트 없이 학습·KEEP을 허용하는지**(11절 33) (4) **절대 비용·p95 상한과 계약 통과 기준**을 누가 확정하는지(11절 34) (5) 봉인 세트 제작(11절 10), 개발 세트 정답 방식(11절 11), strict 폴백(11절 21), 대상 모델(11절 24), 교사 모델과 정답 생성 방식(11절 38). 11절 사람 결정 중 기록이 없는 항목이 있으면 job을 만들지 않는다(S0 (마))
2. 구성 고정: 판정 호출 temperature 0(seed는 best effort라 기대지 않음). **이 단계에서는 평가 세트를 돌리지 않는다.** 구성: (가) 기본 모델 + 풀 프롬프트 (나) 교사 모델(11절 38에서 정함) + 풀 프롬프트 (다) 기본 모델 + 짧은 지시문 (라) FT 모델 + 짧은 지시문. 6.3절의 (a) 규칙만은 공개 회귀 확인에만 쓰고, (b)는 (가)에 대응한다. (c) 모델 B는 교사 모델을 MODEL_B로 정할 때만 (나)와 같다
3. 라벨 검사: V1~V7 통과만으로는 정답 품질을 보장하지 못한다. 1단계 정책을 코드로 옮긴 **판정 정책 검사기**로 모든 정답을 검사한다: 판정이 정책 함수 결과와 같은지, 판정별로 허용된 reasons인지, conflicts의 출처가 실제로 어긋난 신호의 출처인지, actions·customs의 숫자도 입력에 있는지. 허용 reasons 규칙은 D3에서 B08 입력·라벨을 고친 뒤 만들고, 예외는 사람 결정과 테스트로 남긴다(라운드 17 L5). all-clear ETA 근거 분기도 라우터와 똑같이 검사기와 학습·개발·평가 라벨에 적용한다. 기존 all-clear fine 라벨은 이 분기로 다시 검사한다(라운드 19). 통과율 100% 아니면 중단
4. 사람 검토: 경계 사례와 D1~D9 관련 칸 전수, 나머지 층별 표본
5. 진단 (게이트 아님): 짧은 지시문 + 고정 few-shot 5개로 **개발 세트**를 5회. 틀리는 칸을 찾아 학습 데이터를 보강한다. 평가 세트(공개 회귀·봉인)는 쓰지 않는다
6. 형식 사전 검사: 파일 형식, 토큰 길이, 중복, 판정 분포, 다섯 용도 사이의 문항·fixture·근접 변형 겹침 0건
   - **진행 중단 조건 S1 (11절 27)**: 선택 모델·플랫폼·학습/검증 건수·epoch·교사 정답 생성·평가 호출·재시도·적용 가격과 총 예산 상한을 확정하고 계산표를 저장한다. **하나라도 미확정·미산출이거나 예상 총비용이 상한을 넘으면 job 생성 금지**(라운드 17 C4). 기존 $5~8·$11~19는 쓰지 않는다
   - **진행 중단 조건 S2 (11절 26b)**: Vertex를 선택하면 대상 프로젝트·리전·서비스 계정의 튜닝 권한, 선택 모델 지원, 크레딧 적용 증거, 생성 모델과 평가 모델의 회사 분리를 기록한다. **하나라도 확인 기록이 없거나 실패하면 job 생성 금지.** OpenAI를 선택하면 "이번 경로에 적용 안 됨"
   - **진행 중단 조건 S3 (6a·6b)**: 선택 경로의 사전 접근 점검(콘솔 파인튜닝 화면, 파일 업로드, API 키 권한)과 6b 스키마 호환 확인 결과를 기록한다. **실패·미확인이면 job 생성 금지.** 생성 요청이 거부되어 job ID가 발급되지 않았을 때만 job 0개로 기록한다. 요청이 접수된 뒤의 실패는 1개 사용으로 센다
   - 6b. 스키마 호환: 선택 모델과 실제 JUDGE_SCHEMA 조합의 호환성은 학습 전에 확인할 수 없다(11절 19b, OpenAI 경로). 선택 플랫폼의 기본 모델 + 짧은 지시문 + strict 호출이 파싱을 통과한 기록이 없으면 job을 만들지 않는다(S3에 포함). Vertex를 고르면 그 플랫폼의 스키마 계약으로 같은 확인을 한다
7. 학습 1회: 학습 세트 + 내부 검증. job 상태가 failed가 아니면 평가 없이 버리지 않는다. 체크포인트 보관·호출 방식과 스키마 계약은 **선택 플랫폼별로** 확인한다. OpenAI는 마지막 3 epoch 체크포인트를 모델처럼 부를 수 있다(14절). Vertex는 별도 확인이 필요하다(라운드 17 L6). 최종 모델과 체크포인트를 내부 검증·개발 세트로 비교해 하나를 고른다. 손실 곡선은 기록만 한다. 첫 job이 failed면 이 문서 범위에서 재학습은 없다(1회 전제)
8. 평가 캠페인 1회: 모든 구성·반복 횟수·판정식·결측 처리·첫 스키마 요청 워밍업 조건을 학습 전에 고정하고, 봉인 평가 세트와 공개 회귀 세트로 (가)(나)(다)(라)를 같은 날 5회씩 돌린다. 그 결과로 모델·체크포인트·게이트를 바꿔 재평가하지 않는다(라운드 17 L4)
   - 정답 정의: expected_verdict와 expected_status가 둘 다 일치. 식별 오확정·주입·파싱도 같은 정의로 모든 구성에서 센다
   - **봉인 세트가 없으면**: 공개 회귀 결과만 "탐색 결과"로 기록하고 KEEP·서비스 채택을 하지 않는다. 봉인 세트 없이 job을 만들려면 "탐색용 job"임을 사람이 따로 승인한다(라운드 17 C2, 11절 33)
   - **절대 게이트 (상대 비교와 별도, 하나라도 못 지키면 DISCARD)**: act 누락 0, 식별 오확정 0, 스키마 통과율 95% 이상, 주입 오작동 0, 사전 승인된 절대 p95 상한과 요청당 총비용 상한 이하(라운드 17 C3, PRD 8절, 11절 34)
   - **상대 비교 (모두 만족해야 KEEP)**: act_recall 5회 모두 act 정답 전부. (라)의 정답 수 5회 평균 ≥ (가), (라)의 최저 회차 ≥ (가)의 최저 회차. V1~V7 위반율·파싱 실패 ≤ (가). 재시도 포함 요청당 총비용 < (가). p95 ≤ (가). 문항별로 (가)는 맞고 (라)가 틀린 문항 목록을 남긴다
   - 주입·식별·정책 결함이 있으면 상대 성능과 무관하게 DISCARD
   - (라)가 (가)는 이기고 (나)나 (다)와 차이가 없으면 "파인튜닝 효과 미확인"으로 기록한다
   - 보고 범위: KEEP은 사전 고정된 봉인 사례에서의 채택 판단이다. 문항별 실패·표본 수·반복 변동을 같이 보고하고 일반화 성능 보장으로 쓰지 않는다(라운드 17 E3). 공개 회귀 세트는 act 11건 중 6건이 sales_date_exceeded 단독이다. 봉인 세트의 act 수와 분포는 제작 뒤 따로 적는다

### 라운드 1 (B, 2026-09-28)

결론: 문서대로 지금 돌리면 안 된다. 방향은 맞는데 선행 수정 6개가 먼저다.

플로우 확인: POST /api/agent → 통관조회 → 선박식별 → 도구 4종 → signals.py:57 1층 계산 → llm.py:339 judge() (system=judge 프롬프트+skills 전문, user=_judge_input JSON, strict schema) → validate.py:29 V1~V7, 위반 시 최대 3회 재시도. FT 대상은 judge() 하나. 코드에 FT 분기 없음, 제안 상태.

1. D1~D8 라벨 모순 8건이 가장 크다. D1 목적지 단독, D2 항해상태 단독(문서 watch vs 평가셋 fine), D3 anchor_wait는 signals.py:155에 triggered 경로가 없는데 B08 정답은 act. 이대로 증류하면 모순을 모델에 고정한다. 정운님과 합의 필수
2. V7 날짜 폭탄. _judge_input()에 날짜 원문이 없어 answer에 날짜를 쓰면 validate.py:65에 걸린다. ft_label.py가 V7로 거르면 날짜 정답이 대량 탈락한다. 입력에 날짜를 넣을지, answer에서 날짜를 금지할지 정해야 한다
3. V6 이름 불일치. chosen은 shipfinder/mof/...만 되는데(validate.py:60) 우선순위 이름은 mof_actual/mof_planned/... judge 프롬프트에 지시가 없어 재시도를 유발한다. FT 전에 프롬프트 한 줄 추가
4. 구현 누락 3개. llm.py:311은 항상 skills 전문 주입이라 짧은 시스템 분기 없음. rules.md 해시 체크(EC-01), OpenAI 직접 호출도 없음. Spec "정할 것" 4개 미정
5. 290건으로 부족할 확률이 높다. strict JSON + 한국어 2~3문장 + 규칙 판정을 290건으로 외우게 하기 어렵다. 값 변형은 "값 무시, 모양 외우기" 위험. few-shot 선행 측정(Q14)을 먼저 하라
6. 평가가 운이다. 판정 21~23건 중 act 11건에서 act_recall 1.0은 1건만 삐끗해도 탈락. 반복·temperature·seed 고정 없이 1회 통과는 의미 없다. 최소 5회 반복 + 신뢰구간

순서 제안: label-decisions-prompt로 D1~D8 합의 → V6/V7 입력·프롬프트 수정 → few-shot 선행 실험 → FT job 1회. 지금 돌리면 라벨 모순 + V7 실패로 DISCARD될 확률이 높다.
