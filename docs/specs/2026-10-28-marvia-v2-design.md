# Marvia v2 설계

- 상태: 검토 중
- 브랜치: `v2` (v1은 태그 `v1-final`, `main`은 v1으로 동결)
- 성격: 개인 사이드 프로젝트. 3차 팀 프로젝트와 관계없고 3차 과제 기준(게이트·가산점·청크 수)은 적용하지 않는다.
- 참고 자료: v1 코드(`v1-final`), 위키 `Projects/Team_Projects/Proj3/주제확정전/`(3차에서 검토했던 Marvia 방향), 위키 `기술스택/에이전트-기술/`(기술 카탈로그, 범용 에이전트 구현 비교). 참고만 하고 그대로 옮기지 않는다.

## 1. 무엇을 만드나

**한 줄 정의**: 소량 수입 셀러가 가진 어떤 단서로든 화물을 찾아, 출항부터 반출까지 내 화물의 실시간 상태와 내 품목 이력을 그 시점에 유효한 법령·고시에 맞대어 "언제, 무엇을, 왜 해야 하는지"를 근거와 함께 답하고, 막히면 다음 길을 제안하는 에이전트.

| 항목 | 내용 |
|---|---|
| 기준 사용자 | 소량 수입 셀러(스마트스토어·쿠팡 수입 판매자). 포워더·관세사·무역 담당자도 쓸 수 있게 화물 중심으로 설계하고, 사용자별 차이(설명 깊이 등)는 설정과 장기 기억으로 맞춘다 |
| 구간 | 해상 운송의 출항 → 입항·하선 → 통관 → 보세구역 반출 완료. 육상 운송은 하지 않는다 |
| 항만·국가 | 코드에 고정하지 않고 데이터로 둔다. 1차 검증은 부산·인천, 출발 국가 중국 |
| 하지 않는 일 | 통관 가부 판단, HS 코드 확정, 세액 판정. 근거가 없으면 단정하지 않고 "관세사에게 물을 질문"을 만들어 준다 |

**범용 도구와 다른 점**: 3차 검토 때 Codex는 법령 조문 질문을 대부분 맞혔고, 진 곳은 내 화물 실시간 상태, 여러 첨부 모아 세기, 품목분류 결정 사유 본문이었다(위키 Proj3 `Marvia-방향.md`). 그래서 차이는 "법을 아는 것"이 아니라 내 화물 상태·내 품목 이력·변동 정보를 조문에 맞대고 기한과 검사 여부를 코드로 일관되게 계산하는 데서 낸다.

| 8 | RAG는 세 층: A 정리된 코퍼스(조문 인용) / B 에이전트가 여러 번 검색 / C 웹 검색(2차) | 자유도를 높이되 근거 신뢰도를 층으로 구분한다 |

| 11 | 일정: 일요일(11-01)까지 1차 전체를 목표로 하고, 밀리면 정해 둔 순서대로 뺀다 | 1차 범위를 정해 둔 순서로 지키기 위해 |

## 3. 전체 구조

```
[화면] Next.js ── AG-UI 이벤트로 계획·진행·선택지·승인 카드를 실시간 표시
   │  AG-UI (SSE)
[API] FastAPI ── ag-ui-langgraph 엔드포인트, 로그인
   │
[에이전트] LangGraph
  메인 그래프 (직접 짠 StateGraph) ── 루프: `create_agent` + 도메인 도구 + 미들웨어(할 일 목록, 승인, 호출 한도)
  │  호출 한도 → 마무리 노드(부분 답). 고정 계획자는 `MARVIA_LOOP` 뒤의 기준선 길로 둔다
  ├─ 식별 서브그래프 ── 단서 → CargoIdentity (애매하면 선택지 interrupt)
  ├─ RAG 서브그래프 (Agentic RAG, 하이브리드 RAG)
  │    질의 분석 → ① 하이브리드 검색 + ② GraphRAG → 리랭커 → 근거 채점
  │    → 부족하면 질의 재작성(최대 2회) → unit_id가 붙은 근거 묶음
  ├─ 계산 도구 (코드)
  ├─ 조회 도구 (코드: UNI-PASS, 선박 위치, 해수부)
  ├─ 작성자 (구조화 출력) → 검증자 (코드)
  └─ interrupt: 선택지 질문 / 승인 (서로 다른 통로)
[데이터]
  Postgres(Supabase): 앱 테이블, 조문 단위 + 벡터 + 키워드, 대화 상태(checkpointer), 장기 기억(Store)
  Neo4j: 법령 지식 그래프
[색인 파이프라인] 국가법령정보센터(현행판) → 파싱 → 조·항·호·목 단위 → 맥락 문장 → 임베딩 → Postgres
                                                     └→ 위임·참조(규칙) + 품목·요건(LLM, 사람 검토) → Neo4j
[MCP] 규정 검색을 MCP SDK v2 서버로 공개하고, 에이전트도 같은 서버를 MCP 클라이언트로 호출
[관측·평가] Langfuse 트레이스·프롬프트, 동결 평가셋, GitHub Actions 회귀 검사
```

## 4. 식별

### 4.1 단서 등급

| 등급 | 단서 | 처리 | 차수 |
|---|---|---|---|
| ① 자동 식별 | 화물관리번호, B/L | UNI-PASS로 조회해 확정 | 1차 |
| ① 자동 식별 | 서류 사진, 포워더 메시지 | 글에서 번호를 뽑아 위로 넘김 | 1차 |
| ② 후보 제시 | 선박명·항차, 컨테이너 번호 | 후보를 찾아 좁히고 여럿이면 선택지 | 2차 |
| ③ 안내 | 번호 없음(품목·출발지·예정일) | 필요한 번호와 이유를 설명하고 포워더에게 보낼 문장을 써 줌. 번호를 받아 오면 ①로 | 1차 |

### 4.2 번호 읽기 (코드가 먼저)

- 화물관리번호: 19자리 = MRN 11 + MSN 4 + HSN 4. 앞 11자리 MRN이 해수부 선박운항정보의 `mrNum`과 같아 배를 특정한다(v1 `backend/app/services/judge/customs.py:13`, 실제 B/L로 확인).
- B/L: 영문 접두어 + 숫자. 같은 접두어가 반복되면 그 자리에서 나눈다(`HASL0001HASL0002` → 2건).
- 정리: 공백·하이픈 제거, 대문자화, OCR 혼동 후보(O/0, I/1)는 원본과 함께 후보로 남긴다.
- 나누는 방법이 하나뿐이고 형식 검사를 통과하면 진행하고 "두 건(…)으로 읽었어요"와 "다르게 읽기"를 보여 준다. 여럿이거나 실패하면 선택지 interrupt.
- 서류 사진: OCR(v1 rapidocr 방식 참고) 후 같은 규칙. 메시지: 정규식이 먼저, 정규식이 못 잡은 칸만 LLM 구조화 추출.
- 번호 가림: LLM에 넘기기 전에 실제 번호를 `[BL1]`, `[CARGO1]` 같은 토큰으로 바꾼다. 실제 값은 state의 `masked_map`에만 둔다.

### 4.3 출력 형식 `CargoIdentity`

| 칸 | 뜻 |
|---|---|
| `token` | LLM이 보는 가린 이름(`[BL1]`) |
| `cargo_no`, `bl_no`, `bl_year` | 실제 번호(코드만 봄) |
| `mrn` | 화물관리번호 앞 11자리 |
| `vessel` | 배 이름·호출부호·IMO(알면) |
| `source` | 어떤 단서에서 나왔나(직접 입력, 사진, 메시지) |
| `confidence` | 확정 / 후보 / 미확인 |
| `candidates` | 확정 못 했을 때의 후보 목록 |

화물이 여러 건이면 화물별로 동시에 조회한다(LangGraph `Send`).

## 5. 하이브리드 RAG

### 5.1 코퍼스 (1차)

- 출처: 국가법령정보센터. **현행판만** 받는다(시행일 ≤ 오늘). 3차 측정 때 최신 공포본(시행 예정판)을 받아 온 문제를 반복하지 않는다(위키 Proj3 `evidence/원장.md` 10-28).
- 1차 범위: 대표 질문 3개(첫 수입 요건, 검사로 멈춘 화물, 재수입 정밀검사)에 필요한 문서부터. 관세법·시행령·시행규칙, 수입통관 사무처리에 관한 고시, 보세화물관리에 관한 고시(별표 1 포함), 관리대상화물 관리에 관한 고시, 수입식품안전관리 특별법·시행규칙(별표 10 포함), 수입식품등 신고 및 검사 규정. 그 뒤 3차 측정의 필수 56건으로 넓힌다.
- 이용 조건: 법령·고시는 저작권법 제7조의 보호받지 못하는 저작물이다. 관세청 질의회신·품목분류 결정사례는 재배포 협의 대상이라 넣지 않는다.

### 5.2 파싱과 단위

- HTML 조문은 구조대로, HWPX 별표는 zip 안 XML을 직접 읽고, PDF는 Docling. 2단 조판 PDF는 단이 섞이는지 확인한다.
- 자르는 단위는 조·항·호·목. 별표는 행 또는 목 단위.
- `unit_id` 형식: `{법령ID}@{시행일}#제26조.1항.2호.가목`. 같은 키를 Postgres와 Neo4j가 함께 쓴다.
- 메타데이터: 법령명, 종류(법률·시행령·시행규칙·고시·별표), 시행일, 출처 URL, 본문 sha256.

### 5.3 색인

- 맥락 문장(Contextual Retrieval): 단위마다 "이 조문은 ○○법 제○장 ○○에 관한 것으로…" 같은 한두 문장을 LLM이 색인 때 한 번 붙인다. 켜기 전후를 평가셋으로 비교한다. 결과(11-06, 계획 4a): 켠 색인으로 에이전트 길 30문항을 돌린 값이 정답 근거 인용률 0.75(끈 기준 실행과 같음), 잘못된 근거 0.30(0.40), R@8 0.46(0.50), MRR 0.35(0.42)라서 기본 색인은 맥락 문장 없이 둔다. 두 실행은 실행기 코드가 하나 다르고(감시 도구를 묶은 것, 모델이 보는 도구 목록에 `watch_cargo`가 늘었다) 설정마다 한 번만 돌렸으므로 같은 코드로 한 번 더 잰 뒤 정한다.
- 임베딩: Voyage AI의 `voyage-4`(1024차원, 모델은 설정 값). 색인은 `input_type=document`, 질문은 `query`로 보낸다. pgvector HNSW 인덱스.
- 키워드: kiwipiepy로 형태소를 나눠 `tsvector('simple')`에 넣는다(Postgres 기본 전문 검색에는 한국어 사전이 없다).

### 5.4 검색 흐름

1. 질의 분석(LLM, 구조화 출력): 질문 유형(문구 해석 / 위임 사슬 / 다단계 요건 / 화물 결합), 기준 날짜, 키워드.
2. ① 하이브리드 검색: 벡터 상위 k + 키워드 상위 k를 RRF로 합친다.
3. ② GraphRAG: ①의 상위 단위나 질의에서 뽑은 품목에서 출발해 1~2단계 관계를 따라간다(Cypher).
4. 합친 후보를 리랭커로 정렬한다.
5. 근거 채점(LLM, 구조화 출력): 충분 / 부족 + 부족한 이유.
6. 부족하면 질의를 고쳐 다시(최대 2회). 그래도 부족하면 막힘 처리로 넘긴다.
7. 결과: 근거 묶음 `[{unit_id, 원문, 법령명, 시행일, 출처 URL, 점수}]`.

### 5.5 GraphRAG (Neo4j)

| 노드 | 예 |
|---|---|
| `Law` | 관세법, 수입통관 사무처리에 관한 고시 |
| `Unit` | 조문 단위(`unit_id`) |
| `Item` | 실리콘 주방 매트, 건고추 |
| `Requirement` | 식약처 수입신고, 정밀검사, 식물검역 |
| `Document` | 수입신고확인증, 해외제조업소 등록증 |
| `Agency` | 식약처, 농림축산검역본부 |

| 관계 | 만드는 방법 |
|---|---|
| `(Unit)-[:PART_OF]->(Law)` | 구조 파싱 |
| `(Law)-[:DELEGATES_TO]->(Law)` | 법률 → 시행령 → 시행규칙 → 고시 위임 (규칙 추출) |
| `(Unit)-[:REFERS_TO]->(Unit)` | "제○조에 따라" 같은 참조 (정규식 추출) |
| `(Item)-[:REQUIRES]->(Requirement)`, `(Requirement)-[:NEEDS]->(Document)`, `(Requirement)-[:BY]->(Agency)`, `(Requirement)-[:GROUNDED_IN]->(Unit)` | LLM 추출 후 사람 검토. 1차는 대표 품목 2종(실리콘 주방 매트, 건고추) |

라이브러리: neo4j 드라이버, neo4j-graphrag(1.23.0에 `HybridRetriever`·`HybridCypherRetriever`가 있다, 10-28 확인).

### 5.6 인용 규칙

답에 쓰는 인용은 근거 묶음에 있는 `unit_id`뿐이다. 계산 도구는 날짜·조건만 돌려주고 인용을 만들지 않는다. 검증자가 코드로 확인한다.

## 6. 에이전트 그래프

### 6.1 루프 (11-06 바꿈)

메인 그래프는 LangGraph `StateGraph`로 직접 짠다(흐름을 보고 배우기 위해서). 흐름은 식별 → 루프 → 작성자 → 검증자 → 답 / 부분 답이다. 루프는 LangChain `create_agent`다. 모델이 도메인 도구를 골라 부르고, 병렬 호출을 허용하고, 더 부를 도구가 없으면 끝난다.

- 라이브러리 기능을 그대로 쓴다: 도구 루프, 병렬 도구 호출, `TodoListMiddleware`, `HumanInTheLoopMiddleware`, 도구별 호출 한도.
- 도메인 보장은 우리 코드가 맡는다.
  - 도구는 가린 토큰만 받고 돌려준다.
  - 근거와 계산 결과는 합치는 함수(reducer)가 붙은 state 칸에 도구가 쓴다.
  - Guards 미들웨어: 모델 호출 전과 검색 전의 LLM 호출 수 상한, LLM 실패는 부분 답으로, `ask_user`는 혼자 부르기, 진행 중인 할 일은 하나.
  - 검증자는 루프 뒤에 그대로 두고 state 칸만 읽는다.
  - 루프는 모으기만 하고 답은 기존 작성자가 쓴다(루프 안 구조화 응답과 재진입은 쓰지 않는다).
- 고정 계획자(계획 노드가 LLM 구조화 출력으로 할 일 목록을 만들고 실행 노드가 보냄)는 비교 기준선이자 대체 길로 남기고 `MARVIA_LOOP`로 고른다(기본값 `agent`, 11-06 평가셋 기준 실행으로 정함, 821c8e2).
- 대화 기록은 thread마다 차례를 넘어 남는다. 긴 기록은 메인 그래프의 `brief` 노드가 차례를 시작할 때 요약한다(11-06 계획 3d). 루프 안에서 요약하지 않는 까닭은 서브그래프가 끝날 때 자기 값을 부모 reducer에 넘길 뿐이라 부모의 옛 메시지를 줄이지 못하기 때문이다 [실측 11-06: 기록이 `['q','a1','q', 요약, 'a2']`로 끼었다]. 요약 호출도 LLM 호출 수에 든다.
- 계획 3d의 기능(차례를 넘는 기억과 요약, 장기 기억 읽기·설정, 조사 서브에이전트, 색인 밖 공식 조회, 감시)은 에이전트 길에만 있다. 계획자 길은 계획 3a 그대로이고, 여러 화물 병렬 조회만 식별 단계라 두 길이 함께 쓴다 (11-06).
- 다섯 질문 비교: 처음 비교(11-06, 685d89c)에서 에이전트 길은 근거나 계산이 있는 답 4/5(계획자 3/5)였고 LLM 호출이 질문당 12회 기준을 넘었다(19·19·17회, 공식으로 센 값). 튜닝 뒤 다시 잰 비교(11-06, 9a8f7af, 실제 호출을 콜백으로 셈)는 계획자 길 4/5, 호출 6·5·5·20·19회(중앙값 6, 최대 20), $0.0230이고 에이전트 길 4/5, 호출 5·18·11·9·3회(중앙값 9, 최대 18), $0.0285다 [실측 11-06]. 에이전트 길이 한 질문에서 기준을 넘어(18회) 그때는 기본값을 계획자로 뒀다.
- 기본 길 결정(11-06, 계획 4a): 평가셋 v1 30문항을 Haiku 5.5로 두 길에 돌린 기준 실행(ae1891c)에서 미리 정한 일곱 기준을 에이전트 길이 모두 넘어 기본값을 `agent`로 바꿨다(821c8e2). 오류·새는 번호·상한 넘음 0, 정답 근거 인용률 0.75(계획자 0.50), 근거 있는 답 0.88(0.62), 행동 정확도 0.80(0.63), 근거 없는 답 0.00(0.00), LLM 호출 중앙값 8.5·최대 17(기준 12·22 이하), 문항당 평균 $0.0050(기준 $0.02 이하) [실측 11-06]. 계획자 길은 `MARVIA_LOOP=planner`로 남는 기준선이다. 에이전트 길의 잘못된 근거 비율은 0.40으로 목표 0.3 이하에 못 미쳤고 튜닝이 다음 계획의 첫 일이다. 판정 기준 밖에서는 에이전트 길이 더 나쁜 지표가 있다: 잘못된 근거 0.40(계획자 0.29), R@8 0.50(0.75), U05~U10 행동 정확도 2/6(5/6) [실측 11-06]. 비관련 합계가 에이전트 쪽이 나은 것(0.6 대 0.5)은 계획자 길에 없는 거절 기능으로 U01~U04를 맞혔기 때문이다. 판정은 미리 정한 기준이라 그대로 두고 U05~U10을 튜닝 목표에 넣는다. 독립 리뷰 뒤 코드(`0848c2c`)로 에이전트 길을 다시 돌린 값은 행동 정확도 0.73, MRR 0.34, 잘못된 근거 0.43이고 R13·U07 두 문항이 뒤집혔다. 한 번 실행한 값끼리는 0.07쯤 흔들린다 [실측 11-06].

| `plan` | 계획자 길의 할 일 `[{step, status}]`, 진행 중은 한 번에 하나 |

### 6.3 interrupt 두 통로

- 선택지 질문: `{"kind": "choice", "question", "options": [{"label", "description"}], "recommended": 0}` → 재개 값 `{"selected": i, "custom": "..."}`. 화면이 "기타" 입력칸과 "권장안으로 진행" 버튼을 붙인다. 답이 없는 재개 `{"timeout": true}`(시간은 서버나 화면이 잰다)는 권장안으로 진행하고 `assumptions`에 남긴다. `ask_user`는 그 차례의 도구 호출 중 혼자여야 한다.
- 승인: `HumanInTheLoopMiddleware`의 묶음(batched) 모양을 따른다. `{"action_requests": [{"name", "args", "description"}], "review_configs": [...]}` → 재개 값 `{"decisions": [{"type": "approve" | "edit" | "reject", ...}]}`. 카드 설명에는 저장할 사실을 보인다. 권한 모드는 ask/auto이고, auto여도 밖으로 나가는 메시지는 늘 묻고(always_ask), 모르는 값은 묻는다.
- 승인 지점: 품목 카드 저장·수정, 설명 깊이 저장(`save_preference`), 감시 목록 등록(`watch_cargo`)은 auto에서도 늘 묻는다(`approval.always_ask`). 카드에서 고친(edit) 인자로 도구가 돌고 고친 값도 같은 검사를 받는다 (시험 있음, 11-06). 밖으로 나가는 메시지 발송(2차), 웹 자료를 코퍼스에 추가(2차).
- 질문과 승인은 루프(`create_agent` 서브그래프) 안에서도 멈춘다(`ask_user` 도구, 승인 미들웨어). 서브그래프는 부모 checkpointer를 물려받아 같은 thread로 이어 간다. 식별 서브그래프는 전처럼 "물을 것"을 돌려주고 메인 그래프가 묻는다 (11-06 바꿈).
- 재개하면 그 노드(도구)가 처음부터 다시 실행되므로 interrupt 앞에는 바깥 호출을 두지 않는다. 병렬 도구는 호출마다 따로 돌아, 앞 단계에서 끝난 도구는 재개 때 다시 돌지 않는다 (11-06 실측).

### 6.4 한도와 마무리

`recursion_limit`과 LLM 호출 수 상한에 닿으면 에러 대신 마무리 노드로 간다. 마무리 노드는 현재 판정, 빠진 근거, 다음 선택지를 담은 부분 답을 낸다. 노드마다 재시도·타임아웃을 둔다. 루프의 LLM 호출 상한은 모델 호출과 검색 안의 RAG 호출을 함께 세고, 모델 호출 전과 검색 전마다 확인한다. 작성자는 따로 한도(`max_write_attempts`)를 가진다. 조사 서브에이전트(`research`)는 부모와 같은 LLM 호출·검색 상한을 이어 세고, 이번 차례 검색 상한을 부모가 다 썼으면 돌리지 않고 거절한다. 서브의 모델이 실패하면 부모를 다시 부르지 않고 부분 답으로 끝난다 (11-06).

### 6.5 검증자 (코드)

| 규칙 | 내용 |
|---|---|
| 인용 | 답의 인용이 모두 `evidence`의 `unit_id`인가 |
| 숫자 | 답의 날짜·일수·등급이 `calc` 결과와 같은가 |
| 금지 | 통관 가부, HS 확정, 세액을 단정하지 않았나 |
| 번호 | 실제 번호가 아닌 가린 토큰만 썼나(화면에 보낼 때 코드가 되돌린다) |
| 근거에 없음 (11-06) | 작성자가 `not_in_evidence`를 켜면 "근거가 있는데 인용이 없다"는 적용하지 않는다(상관없는 조문 인용을 막는다). 켰는데 코드가 계산한 값이나 찾은 화물이 있으면 위반이다. 칸이 참이면 코드가 `NOT_FOUND_LEAD`를 답 앞에 붙인다 |
| 위치 | 오래된 위치를 "현재 위치"라고 쓰지 않았나 (v1 규칙 참고). 선박 위치 조회가 들어올 때까지 미룬다. 선박 위치 조회를 넣는 계획에서 정한다 (11-02) |

위반이면 작성자에게 한 번 고치게 하고, 또 위반이면 부분 답으로 간다.

| 도구 | 내용 |
|---|---|
| `grade`, `confidence`, `schedule` | 판정 네 칸 중 세 칸. 등급(순항·주의·경계·긴급), 확신(확실·부분·불명), 일정(정시·우려·지연·초과). 단계 칸은 UNI-PASS 단계에서 정한다. 입력 오류로 보이는 신호는 등급 대신 확신을 낮춘다. 판매일 넘김은 따로 신호를 두지 않고 여유 일수로 판단한다. 기준과 신호 목록은 `rules/verdict.yaml`. 부산 고정 규칙은 항만 데이터로 바꾼다 |
| `trusted_eta`, `days_margin` | 믿을 ETA와 판매 예정일까지 여유 |
| `import_deadlines` | 반입 뒤 신고 기한 등 날짜 계산 |
| `reimport_check` | 재수입 물품이 서류검사 대상인지 본다. 서류검사 대상은 수입식품법 시행규칙 별표 9 제2호가목7)이고, 그 조건인 동일사 동일수입식품등은 별표 10 제4호(1차는 다목 농산물·임산물, 마목 기구·용기·포장)다. 다시 정밀검사가 되는 사유(별표 10 제1~3호, 별표 9 제2호다목5)·제3호가목5))도 본다. 결과는 "서류검사 요건 충족 / 정밀검사 대상 / 사실 부족 / 대상 아님"이고 "면제"라고 단정하지 않는다. 재량 검사(무작위표본검사 등)는 늘 단서로 붙인다 (11-02) |

임계값과 목록은 규칙 데이터 파일(YAML)에 두고 코드가 읽는다. 항만별 값(장치기간 등)은 항만 데이터 표에 둔다.

### 7.2 조회 도구

| 도구 | 내용 |
|---|---|
| `unipass_cargo` | 화물통관진행정보. 화물관리번호 또는 B/L + 연도. B/L 연도 기본값이 올해라 지난해 B/L이 "없음"으로 나올 수 있으니 연도를 확인한다 |
| `vessel_position` | ShipFinder 위치·후보 |
| `port_schedule` | 해수부 입항 예정·실적. 해외 지역에서 막혀 기존 서울 Cloud Run 릴레이를 쓴다 |
| `recall_memory` | 저장한 품목 카드·설명 깊이를 `<stored_memory>` 데이터 태그 안에서만 돌려준다 (11-06) |
| `save_preference` | 설명 깊이(규칙 `memory.depths`의 값)만 받아 승인 뒤에 저장한다. 작성자는 코드로 읽은 깊이로 쓰고 허용 목록 밖 값은 기본값을 쓴다 (11-06) |
| `research` | 법령 검색만 하는 조사 서브에이전트(`search_law`·`get_provision`뿐). 부모에게 요약 한 줄과 찾은 조문 줄만 돌려주고 조문은 근거 묶음에 합친다 (11-06) |
| `official_lookup` | 색인 밖 법령을 국가법령정보센터에서 이름으로 찾는다. 허용한 호스트(`official.allowed_hosts`)만 부르고 넘겨 주는 주소는 따라가지 않으며, 번호·토큰이 든 이름은 보내지 않는다. 제목은 길이 상한(`official.max_title`)을 두고 데이터 태그 안에서만 모델에 간다. 인용할 수 없다 (11-06) |
| `watch_cargo` | 승인 뒤 화물을 감시 목록에 넣는다. BL·CARGO 토큰만 받고 읽지 못한 토큰은 넣지 않는다. 주기 실행 스크립트가 다시 조회해 단계 변화를 기록한다 (11-06) |

번호가 여럿이면 조회 서브그래프가 `Send` 갈래로 함께 조회한다. 토큰은 나누기 전에 정하고 결과는 순서 번호로 모으며 번호 하나의 오류는 결과로 남겨 나머지를 막지 않는다. 동시 실행 수는 `loop.max_concurrency`가 막는데 그래프 한 층마다 걸려, 도구 안에서 부른 조회 둘이 겹치면 상한의 두 배까지 갈 수 있다(실제 클라이언트의 전역 세마포어는 done 2.3) (11-06).

UNI-PASS 같은 외부 조회 호출은 타임아웃, 재시도 2회, 실패하면 `{error: {code, message, retryable}}`을 돌려준다. 색인 밖 공식 조회(`official_lookup`)는 재시도 없이 한 번 부르고(타임아웃 `official.timeout_s`) 실패는 도구 실패로 남긴다. 응답 크기 상한은 아직 없다 (11-06). 키 없이 도는 재생 모드를 두고, 저장소에는 형식만 같은 가공 데이터만 넣는다(UNI-PASS 약관상 실제 응답은 넣지 않는다).

## 8. 데이터와 기억

- Postgres(Supabase)
  - `users`, `cargos`(사용자별 화물: 가린 번호와 해시, 마지막 상태), `corpus_units`(`unit_id`, 원문, 맥락 문장, 임베딩, 키워드 tsvector, 메타데이터)
  - LangGraph checkpointer·Store 테이블은 라이브러리가 만든다. 실제 실행은 Postgres(`PostgresSaver`·`PostgresStore`)에 두고 시험은 메모리를 쓴다 (11-06)
  - 체크포인트는 AES-GCM(`EncryptedSerializer`)으로 암호화한다. 키는 `MARVIA_DATA_KEY`에서 HKDF(info `marvia-checkpoint`)로 뽑고, 키가 없거나 틀리면 실행 길이 열리기 전에 멈춘다. 문자열 칸 `text`·`answer`는 라이브러리가 직렬화기를 거치지 않고 `checkpoints` 표에 그대로 넣어 평문으로 남는다. 서버 가장자리에서 되돌려 푸는 화면 계획에서 닫는다 (done 4.1) (11-06)
  - 감시 표(`watches`, `watch_events`): 실제 번호는 앱이 Fernet으로 암호화해 두고 같은 번호 검사는 HMAC-SHA256 해시로 한다. 암호화 키와 해시 키는 `MARVIA_DATA_KEY`에서 HKDF로 따로 뽑는다. 키가 없거나 Fernet 키 모양이 아니면 감시를 끈다. 변화는 답에 보인 뒤에만 본 것으로 표시한다. `forget_user`가 한 사용자의 감시와 변화 기록을 지운다 (11-06)
  - 마이그레이션은 SQL 파일로 두고 API 시작 때 적용한다
- Store 네임스페이스: `("users", uid, "items")` 품목 카드, `("users", uid, "prefs")` 설명 깊이 같은 설정(값은 규칙의 목록 안에서만)
- 품목 카드는 승인 뒤에만 Store `("users", uid, "items")`에 저장한다. 이름은 짧게(규칙 `memory.max_item_name`), 화물 번호·토큰·문장 부호를 넣지 않는다 (11-06).
- 저장 기준: 승인된, 다음 수입에도 유효한 사실만 저장한다. 이번 대화 값은 state에만 둔다. B/L 원문과 지시문처럼 보이는 문장은 저장하지 않는다.
- Neo4j: 5.5절 그래프. 개발은 Docker, 배포는 AuraDB 무료판(한도 확인 필요).

## 11. 평가와 관측

- 평가셋 v1 30건은 `eval/set_v1.yaml`에 있다. 초안은 AI 도구로 쓰고, 정답 근거는 초안을 쓰지 않은 검토가 코퍼스 원문과 대조해(30건 중 19건 맞음, 11건 고침, 기록은 `eval/gold_check_v1.md`) sha256으로 동결했다(11-06). 사람이 평가셋을 확정하는 일과 사람 채점 10건은 직접 할 일로 남아 있다.
  - 관련 15: 요건, 보류·검사, 재수입, 식별(붙여 쓴 번호 포함), 화물 + 조문 결합
  - 비관련 10: 도메인 밖, 코퍼스에 없는 대상, 있는 대상의 없는 항목, 기준 시점이 다른 질문
  - 막힘 행동 5: 정답이 "선택지 제시" 또는 "부분 답"인 문항
  - 정답 근거는 `unit_id`로 적는다
- 평가셋 v2(11-06, 계획 4a-2)는 v1의 질문을 그대로 두고 채점 기준만 고쳤다: 코퍼스에 없는 대상을 묻는 U05~U10은 정직한 "없음"(`not_found`)이 맞고, 식별 문항 R09·R10은 읽은 화물 수와 단계가 맞아야 맞다. 독립 대조(`eval/gold_check_v2.md`) 뒤 sha256으로 동결했고 v1과 그 결과는 남겼다. "없음"은 작성자가 `Draft.not_in_evidence`를 켜면 코드가 정한 문장(`NOT_FOUND_LEAD`)을 답 앞에 붙이고 채점은 그 문장을 찾는다. 정답 행동이 답인 문항에서 이 문장이 붙으면 틀림이다
- 평가셋 v2 결과(11-06, Haiku 5.5, 설정마다 세 번, 평균과 최소~최대): 에이전트 행동 정확도 0.91(0.87~0.93), 계획자 0.68(0.67~0.70). 같은 줄을 v1 채점으로 세면 0.88, 0.63이라 둘의 차이가 채점 기준 변경의 몫이다. 비관련 정확도 1.00은 칸을 켰다는 뜻이고 본문의 정직함은 코드가 확인하지 않는다(계획 4a-2 문서 "읽을 때 알아 둘 것"). CI 문은 v2의 첫 실행 파일로 옮겼다 [실측 11-06]
- 지표 (11-06 구현): 정답 근거 인용률, 잘못된 근거 비율, 행동 정확도와 막힘 행동 정확도, 근거 없이 답한 비율, 계산 정확도, 검색 R@k·MRR, 도구 호출 궤적 통과율은 코드가 센다(`src/marvia/eval/metrics.py`). 11-02 RAG 관찰 세 가지(질문 밖 조문, 한 조문 쏠림, 근거 없이 충분)도 지표다. ragas(faithfulness, context precision·recall)는 우리 의존성과 따로 된 환경에서 Sonnet 5.5 판정으로 잰다. 첫 ragas 실행(`ae1891c` 답)의 faithfulness는 계산 줄이 없는 8문항 0.636, 12문항 전체 0.475다. 계산 문항을 빼는 규칙은 점수를 본 뒤 정했고 화물 문항 R15는 빼지 않았으므로 두 값을 함께 적는다. 다음 실행부터는 충실도 맥락에 답이 인용한 조문과 작성자가 본 계산·화물 줄을 넣고, 정밀도·재현율 맥락은 그 차례 검색이 돌려준 글의 RAG 재순위 앞쪽으로 하며, 계산 문항을 따로 빼지 않는다. 맥락이 빈 충실도·재현율은 0, 정밀도는 못 잰 값으로 세고 채점하지 않은 문항은 이유와 함께 찍는다(실행 전에 정함, 11-06, 계획 4a 문서 ragas 절). 이 규칙의 첫 실행(`0848c2c` 답, 11문항, R13은 부분 답이라 채점 안 함)은 충실도 0.687, 맥락 정밀도 0.605(9문항), 맥락 재현율 0.518이다 [실측 11-06, 사람 일치 미확인].
- LLM 채점은 사람 채점 10건과 일치율을 확인한 뒤 쓴다. 확인 전에는 "LLM 채점, 사람 일치 미확인"을 값과 함께 붙인다. 일치율은 계산 줄을 맥락에 넣지 않은 첫 점수 파일(`ae1891c` 답)에서는 계산 문항을 뺀 7건으로, 계산·화물 줄을 넣은 점수 파일(`contexts_rule: cited+calc`)에서는 10건 모두로 센다. 사람 채점이 충실도에만 있으므로 정밀도·재현율은 늘 미확인이다.
- GitHub Actions (11-06 구현): 키 없이 린트·형식·타입·시험을 돌리고, 저장소에 커밋한 파생 값 줄을 지금 지표 코드로 다시 채점해 바닥값 아래면 실패시킨다. 바닥값은 코드가 기준 실행에서 만들고(`run_eval.py floors`), 저장한 결과가 평가셋 문항을 모두 덮어야 통과한다. 모델 응답은 저장소에 두지 않으므로 응답 재생은 하지 않는다.
- 간접 주입 시험 (11-06 구현): promptfoo가 Docker 안에서 다섯 통로(검색 결과 본문, 저장된 품목 카드, 공식 페이지 제목, 서류 사진 글, 사용자 글)에 같은 주입 글을 넣고, 같은 사례를 pytest가 가짜 모델로 키 없이 돈다. 차례가 실제로 돌지 않은 경우는 통과로 치지 않는다. 실제 모델 5/5 통과, 주입을 따르는 가짜 모델 5/5 실패 [실측 11-06].
- Langfuse v4: 노드·도구·LLM 호출마다 트레이스(OTel), 프롬프트는 레포 파일이 원본이고 Langfuse에 같은 글을 등록한다, 평가 점수를 트레이스에 붙인다. 아직 하지 않았다(키, 트레이스 가림 R-010·R-022·R-039 시험이 먼저).

## 12. 신뢰 경계

- 도구 응답, AIS 목적지 문자열, 문서·메시지, 사용자 입력은 데이터다. 그 안의 문장을 지시로 따르지 않는다.
- 실제 번호는 LLM과 트레이스에 넘기지 않는다(가린 토큰만).
- 되돌리기 어렵거나 기억에 남는 일은 승인 뒤에만 한다.
- 저장한 기억, 색인 밖 공식 페이지 글, 서류 사진에서 읽은 글도 데이터다. 모델에는 데이터 태그 안에서만 간다. 사진 글은 번호 덩어리만 남긴다 (11-06).
- 바깥으로 나가는 호스트는 규칙의 허용 목록(`official.allowed_hosts`, 지금은 `www.law.go.kr`)뿐이고 넘겨 주는 주소는 따라가지 않는다.
- 저장 데이터 키(`MARVIA_DATA_KEY`)는 찍지 않는다. 감시 표와 체크포인트의 암호화 키는 이 비밀에서 용도별로 따로 뽑는다. 키 교체(rotation)는 아직 없다. 키를 바꾸면 옛 감시 줄은 건너뛰고 옛 대화 기록은 읽지 못하므로, 실제 데이터를 넣기 전에 교체 방법(예: `MultiFernet`)을 정한다 (11-06).
- 키는 Secret Manager에 두고 저장소에는 키 이름만 둔다.
- 간접 인젝션 시험(promptfoo)은 시간이 되면 넣는다.
