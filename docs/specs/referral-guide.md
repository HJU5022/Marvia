# 안내처 표

상태: 1(신호별 다음 행선지)과 2(범위 밖 질문)를 구현했다 (PR #71). 재료는 `skills/referrals/rules.md`(새 skills 폴더, "정해야 할 것" 3번의 답), 코드는 `backend/app/services/chat/referrals.py`, 테스트는 `backend/tests/unit/test_referrals.py`.

### 구현 상태

| 항목 | 설계 | 실제 |
|---|---|---|
| 신호별 확인처 | 켜진 신호마다 "확인처:" 한 줄, 두 개까지 | 구현. `referrals.signal_lines/with_signal_lines`, `routers/agent.py`가 LLM 답의 actions 뒤에 붙이고, 설명을 못 만든 폴백에서도 붙인다. `referral_order`, `referral_max: 2`, `referral_prefix`는 rules.md. 입력 오류로 세지 않는 신호는 뺀다 |
| 통관 보류의 UNI-PASS 줄 | 한 줄 더 | 구현 (`signal_referral_links`) |
| navstat_mismatch | 붙이지 않음 | 구현 (rules.md에 항목이 없다) |
| 범위 밖 질문 | 5개 주제를 고정 문장으로 | 5개 구현: air_land, warehouse_date, schedule_change(`require`가 있어야 걸림), weather, import_requirement. B/L이 있는 문장은 건너뛴다 (`services/chat/chat._route`). 주제는 LLM 분류가 아니라 정규식(rules.md `out_of_scope`)이다 |
| 세액·통관 가부 | `BROKER_ONLY`에 확인처 | 구현. `broker_referral`을 `BROKER_ONLY` 끝에 붙인다 (`referrals.broker_tail`) |
| 품목별 요건 답의 한국관세사회 링크 | 붙임 | 안 붙였다. 현재 답은 관세사에게 확인하라는 문장만 있다. 아래 "공식 창구" 표의 `broker_search`는 코드에 쓰이지 않는다 |
| `NOT_IN_SKILLS`, `BROKER_SHORT`에 확인처 | 붙이거나 맞춤 | 바뀌지 않았다 (`services/chat/chat.py`). 아래 "기존 고정 문구와의 관계" 표의 이 줄들은 반영하지 않았다. `CLEARANCE_TAG`는 없앴다 (아래 표) |
| 링크 확인 스크립트 | `scripts/`에 둠 | 만들지 않았다 (scripts/에 없음) |
| 범위 밖 질문 평가 5~10건 | 사람이 따로 | evals/에서 확인하지 못했다 |

## 왜 만드나

마르비아는 답하지 않는 영역이 정해져 있다. 세액·통관 가부 판단, 창고 수령일 예측이 그렇다 (PRD 4절).
지금은 그런 질문에 "관세사에게 문의해 주세요", "자료에 없습니다"로 끝난다 (services/chat/chat.py 고정 문구).
사람만 안내하고 공식 창구는 알려 주지 않는다.
처음에는 웹 검색 답에 출처 링크를 붙였으나, 검색 결과에 따라 매번 달라서 공식 창구가 나온다는 보장이 없었다. 웹 검색 도구는 없앴다 (docs/adr/0020).
판정 답에도 신호가 켜졌을 때 누구에게 무엇을 물어야 하는지가 일정하게 붙지 않는다.

그래서 두 가지를 고정한다.
1. 판정 신호마다 다음 행선지 (아래 "신호별 다음 행선지")
2. 범위 밖 질문마다 "마르비아는 여기까지, 나머지는 여기" (아래 "범위 밖 질문")

품목별 수입 요건(식품, 농산물 검역, 전기용품 인증 등)은 넣지 않는다. 품목마다 기관이 달라 덮을 수 없고, 마르비아의 판정과 무관하다. 그런 질문은 "관세사에게 요건 확인"으로 묶는다.

## 원칙

- 안내 문장과 주소는 코드가 붙인다. LLM은 쓰지 않는다. 일반 설명 단계의 주소 금지 규칙은 그대로 둔다 (marvia-chat-agent 프롬프트 tier 3)
- 주제는 LLM이 아니라 코드가 이미 아는 값으로 고른다: 신호 상태, needs_broker, 질문 분류 결과
- 원본은 rules.md 프론트매터 한 곳에 둔다. 계약 파일이라 PR 리뷰를 거친다
- 사람(포워더, 관세사, 선사, 판매처)을 먼저 적고 공식 창구를 다음에 적는다
- 공식 창구는 정부·공공기관과 법정 단체만 넣는다
- 한 답에 붙는 안내는 두 개까지만
- "괜찮음"(켜진 신호 없음)에는 붙이지 않는다. 불필요한 행동을 시키지 않는다
- 화면은 이미 http·https 주소를 링크로 바꾼다 (web/components/ChatBar.tsx). 웹 수정은 필요 없다

넣지 않기로 한 후보:
- 식약처 수입식품정보마루 등 품목별 기관: 품목 특화라 뺀다 (위 원칙)
- 해수부 Port-MIS: 등록 업체의 입출항 신고용 업무 시스템이다. 일반 수입자용이 아니다
- 부산항만공사: 일반 수입자가 내 배 일정을 보는 화면을 찾지 못했다
- 선사 홈페이지: 선사마다 주소가 다르다. UNI-PASS 선사명(carrier_name)이 있으면 이름만 적는다

## 1. 신호별 다음 행선지

판정 신호(SignalId, schemas/signals.py)가 켜지면 판정 답의 할 일 뒤에 코드가 "확인처:" 한 줄을 붙인다. LLM이 쓴 answer·actions는 건드리지 않는다.

| 신호 | 화면 이름 | 붙일 안내 |
|---|---|---|
| customs_hold | 통관 검사·보류 | 관세사에게 바로 연락하세요. 관세청 고객지원센터 125 (평일 09:00~18:00) |
| dest_changed | 목적지가 부산이 아님 | 포워더에게 목적지가 부산이 아닌 이유(경유인지 변경인지)를 바로 확인하세요. |
| sales_date_exceeded | 판매 예정일 넘김 | 판매처에도 일정이 늦어질 수 있다고 알려 두세요. |
| anchor_wait | 항구 앞 대기 | 포워더에게 접안 예정일을 물어보세요. |
| position_stale | 선박 위치 수신이 끊김 | 포워더에게 배의 현재 위치를 확인해 보세요. |
| eta_conflict | 도착 예정 시각이 서로 다름 | 포워더에게 선사 스케줄 기준 입항 예정일을 확인해 보세요. |
| navstat_mismatch | 항해 상태와 속력이 안 맞음 | 붙이지 않는다. 데이터 오류일 수 있어 지켜본다 |

여러 신호가 켜지면 위 표 순서(위험한 순서)로 두 개까지만 붙인다.
customs_hold일 때는 공식 창구 줄을 하나 더 붙인다: "진행 상황 직접 보기: UNI-PASS 화물진행정보 (https://unipass.customs.go.kr/csp/index.do)".

예시 A: 항구 앞 대기 (모의값)

```
[지켜볼 것] TE****01

배가 부산항 앞에서 18시간째 대기 중입니다. 판매 예정일까지 여유는 2일이라 지금 당장 문제는 아니지만, 대기가 길어지면 여유가 줄어듭니다.

할 일
· 접안 예정일이 언제인지 확인해 두세요.

확인처: 포워더에게 접안 예정일을 물어보세요.
```

예시 B: 통관 검사·보류 (모의값)

```
[지금 조치] TE****01

세관이 이 화물을 검사 대상으로 지정했습니다. 검사가 끝나야 다음 단계로 넘어갑니다.

할 일
· 신고를 맡은 관세사에게 검사 일정과 필요한 서류를 확인하세요.

확인처: 관세사에게 바로 연락하세요. 관세청 고객지원센터 125 (평일 09:00~18:00)
진행 상황 직접 보기: UNI-PASS 화물진행정보 (https://unipass.customs.go.kr/csp/index.do)
```

예시 C: 두 신호가 겹칠 때 (dest_changed + sales_date_exceeded)

```
확인처: 포워더에게 목적지가 부산이 아닌 이유(경유인지 변경인지)를 바로 확인하세요. 판매처에도 일정이 늦어질 수 있다고 알려 두세요.
```

rules.md 프론트매터 모양 (안):

```yaml
signal_referrals:
  customs_hold:        "관세사에게 바로 연락하세요. 관세청 고객지원센터 125 (평일 09:00~18:00)"
  dest_changed:        "포워더에게 목적지가 부산이 아닌 이유(경유인지 변경인지)를 바로 확인하세요."
  sales_date_exceeded: "판매처에도 일정이 늦어질 수 있다고 알려 두세요."
  anchor_wait:         "포워더에게 접안 예정일을 물어보세요."
  position_stale:      "포워더에게 배의 현재 위치를 확인해 보세요."
  eta_conflict:        "포워더에게 선사 스케줄 기준 입항 예정일을 확인해 보세요."
  navstat_mismatch:    null   # 데이터 오류일 수 있어 안내 없이 지켜본다
referral_order: [customs_hold, dest_changed, sales_date_exceeded, anchor_wait, position_stale, eta_conflict]
referral_max: 2
```

## 2. 범위 밖 질문

채팅에서 이런 질문이 오면 LLM 답 대신 코드가 고정 문장으로 답한다.

| 주제 | 사용자 질문 예 | 마르비아 답 |
|---|---|---|
| 항공·육상 | 항공으로 오는 화물도 봐 줄 수 있어? | 마르비아는 부산항으로 들어오는 해상 수입 화물만 확인합니다. 항공·육상 화물은 포워더에게 문의해 주세요. |
| 창고 수령일 | 창고에서 언제 물건 받을 수 있어? | 창고에서 받는 날은 마르비아가 예측하지 않습니다. 반출 일정은 포워더에게 확인해 주세요. 지금 통관 단계는 알려 드릴 수 있어요. |
| 예약·일정 변경 | 배 일정 좀 앞당겨 줄 수 있어? | 마르비아는 예약이나 일정을 바꿀 수 없습니다. 일정 변경은 포워더나 선사에 요청해 주세요. |
| 세액·통관 가부 | 관세 얼마 나와? | 관세·세금·통관 가능 여부는 마르비아가 답하지 않습니다. 관세사에게 문의해 주세요. 확인처: 관세청 고객지원센터 125 · 관세법령정보포털 (https://unipass.customs.go.kr/clip/index.do) |
| 날씨 영향 | 태풍 오는데 내 배 늦어? | 날씨로 늦어질지는 미리 판단하지 않습니다. 실제로 늦어지면 배 위치와 도착 예정에 나타나고, 그때 판정이 바뀝니다. B/L 번호를 알려 주시면 지금 상태를 확인해 드릴게요. |
| 품목별 수입 요건 | 이거 수입하려면 인증 필요해? | 품목별 수입 요건은 마르비아가 판단하지 않습니다. 신고를 맡은 관세사에게 요건을 확인해 주세요. 확인처: 한국관세사회 관세사 찾기 (https://krcaa.or.kr/_Document/Intro/I10203V.aspx?MenuCode=I10203) |
| 자료에 없는 실무 질문 | (Skill·웹·일반 설명 어디에도 없을 때) | 그 내용은 마르비아가 가진 자료에 없습니다. 포워더에게 확인해 주세요. 확인처: 관세청 고객지원센터 125 |

날씨 답은 원인을 단정하지 않는다. 마르비아의 판정은 관측값(위치·속력·입항 신고·통관 단계)에서 나오고, 날씨 영향은 관측할 수 없는 원인 추정이라 넣지 않는다.

rules.md 프론트매터 모양 (안):

```yaml
out_of_scope:
  air_land:        {match: "항공|비행기|육상|트럭|택배", reply: "마르비아는 부산항으로 들어오는 해상 수입 화물만 확인합니다. 항공·육상 화물은 포워더에게 문의해 주세요."}
  warehouse_date:  {match: "창고.*(언제|며칠)|(언제|며칠).*(받|찾)", reply: "창고에서 받는 날은 마르비아가 예측하지 않습니다. 반출 일정은 포워더에게 확인해 주세요. 지금 통관 단계는 알려 드릴 수 있어요."}
  schedule_change: {match: "(앞당|늦춰|바꿔|변경).*(일정|배|예약)", reply: "마르비아는 예약이나 일정을 바꿀 수 없습니다. 일정 변경은 포워더나 선사에 요청해 주세요."}
  weather:         {match: "태풍|날씨|기상|파도", reply: "날씨로 늦어질지는 미리 판단하지 않습니다. 실제로 늦어지면 배 위치와 도착 예정에 나타나고, 그때 판정이 바뀝니다."}
```

정규식은 예시다. 실제로는 채팅 의도 분류 결과와 같이 써서 "창고 위치가 어디야" 같은 질문까지 막지 않게 한다.

## 기존 고정 문구와의 관계

| 지금 문구 (services/chat/chat.py) | 바뀌는 것 |
|---|---|
| BROKER_ONLY, BROKER_SHORT | 위 "세액·통관 가부" 답으로 맞추고 확인처 줄을 붙인다 |
| CLEARANCE_TAG, GENERAL_TAG | 없앴다 (답마다 같은 꼬리표가 붙어 기계 같다는 실사용 지적). "안내용 정보, 실제 처리는 포워더·관세사 확인" 고지는 사이트 이용약관(web/components/LegalLinks.tsx)으로 옮겼다 |
| NOT_IN_SKILLS, SHORT_NOTICE | 위 "자료에 없는 실무 질문" 답으로 맞춘다 |
| follow-up in_scope=false | 그대로 (이 화물 결과 안에서만 답한다는 안내) |

## 구현 범위

- rules.md 프론트매터: signal_referrals, referral_order, referral_max, out_of_scope. 계약 파일 변경이라 PR 리뷰를 거친다
- 판정 응답 조립(코드): 켜진 신호로 확인처 줄을 만들어 actions 뒤에 붙인다. LLM 출력 검증(V1~V7)은 붙이기 전에 끝난다
- services/chat/chat.py: 범위 밖 주제를 먼저 가르고 고정 문장으로 답한다. 기존 고정 문구는 위 표대로 맞춘다
