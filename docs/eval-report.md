# Marvia v2 평가 보고서

이 문서는 Marvia v2를 무엇으로, 어떻게 쟀고, 그 숫자를 어디까지 믿을 수 있는지를 적는다. 모든 숫자에는 잰 커밋과 결과 파일을 붙였다. 결과 파일이 저장소에 없으면 "저장소 밖 원본"이라고 적었고, 그런 값은 저장소만으로는 다시 낼 수 없다. 아직 재지 않은 칸은 "측정 전"으로 두었다.

기준 시점: 2026-11-22, 브랜치 `v2`. 저장소에 있는 결과 파일(`eval/results/`)은 `uv run python scripts/run_eval.py report|spread|verdict ... --set <판>`으로 키 없이 다시 채점해 이 문서의 값과 대조했다. 3.2.1절 검색 값은 `marvia.eval.retrieval.summarize`로, 6절 백분위와 9.3절 쌍별 값은 지표 함수(`marvia.eval.metrics`)로 결과 줄에서 다시 냈다. 쌍별 호출 중앙값은 v3 30문항 줄의 `real_llm_calls` 중앙값이다. 저장소의 결과 파일로 다시 낼 수 없는 값에는 그 자리에 출처("저장소 밖 원본", "계획 4a 문서" 등)를 적었다. 에이전트 측정은 두 가지 조건이 섞여 있어 한 표에 섞어 읽지 않는다.

- Anthropic API로 잰 줄(2026-11-06, 3.1절, 6절): 모델 Haiku 5.5(비교 한 줄은 Sonnet 5.5), UNI-PASS 재생 데이터. 비용과 시간을 쟀다.
- CLI 경유(`MARVIA_LLM_VIA=cli`)로 잰 줄(2026-11-13의 수퍼바이저 비교, 2026-11-20의 배 판정 비교, 3.4절과 9절): 모델 Haiku 5.5, 재생 데이터. 비용과 시간은 재지 않았다. API 키를 쓸 수 없는 기간에 잰 값이라 API 줄과 숫자를 견주지 않는다.
- 검색 값(3.2절)은 LLM 없이 잰 값이다. 질문 글을 그대로 질의로 넣었다.

지금 코드로 다시 잰 에이전트 값은 CLI 경유 값뿐이다. `87d92e8`(API) 뒤에 코퍼스(별표 단위), 지시문, 도구 설명, 검색 코드가 바뀌었다. 그 뒤 에이전트 길을 다시 잰 것은 `48ca3c5`(11-13), `1f32f5f`(11-20)의 CLI 경유 값이고, API로 다시 재는 일은 키가 돌아온 뒤로 남아 있다(7절).

- 왜 바꿨나: 원래 G1은 "정답 근거 인용률 평균 0.75 이상, 행동 정확도 평균 0.87 이상"이라는 절대 숫자를 썼다. 이 두 값은 평가셋 v2를 Anthropic API로 잰 값에서 정했다. 지금은 API 키를 쓸 수 없어 LLM 측정을 CLI 경유로 하고, 평가셋도 v3로 바뀌었다. 조건이 다른 실행에 그 절대 숫자를 그대로 대면 그래프와 상관없이 통과나 실패가 정해진다. 그래서 기준선(그래프 끔)과 후보(그래프 켬)를 같은 조건에서 번갈아 다섯 쌍 돌려 견주는 방식으로 바꿨다.
- 무엇으로 바꿨나: 수퍼바이저 비교에 이미 쓴 규칙(`rules/eval.yaml`의 `comparison`, 코드 `compare_paths`)을 그대로 쓴다. 문(오류 0, 새는 번호 0), 낮지 않음 줄(행동 정확도는 1/30, 정답 근거 인용률은 1/12, 근거 없는 답은 1/15(분모가 답해야 하는 15문항), 상한에 닿은 줄은 3줄 폭), 비용 줄(LLM 호출 중앙값 1.5배 이내), 이김(다섯 번 중 세 번 이상 맞은 문항 수가 2개 이상 많음)이다. 그래프를 기본으로 켜는 것은 "이김"이고 오프라인 검색 조건도 넘을 때만 한다. 그래프를 켜면 배포에 Neo4j가 하나 더 붙기 때문에 나아짐이 보일 때만 켠다. 원래는 "낮지 않음"만 넘어도 켰다.
- 같이 바뀐 것: 오프라인 조건(G1 첫 조건)은 11-07 값이 아니라 측정 커밋에서 다시 잰다(그 뒤 검색 코드가 바뀌었다). 무효 실행은 같은 번호로 많아야 세 번 다시 돈다(원래는 한 번까지). 11-13과 11-20의 CLI 측정과 같은 규칙이고, 11-20에는 CLI 쪽 실패로 무효가 된 실행이 넷이었다. G2는 판정하지 않고 평균과 범위, 문항별 변화만 적고, G3은 계획자 길을 돌리지 않아 판정하지 않으며, G4(R07)는 "세 번 중 두 번"을 다섯 번에 맞게 "다섯 번 중 세 번"으로 바꿨다. G5와 G6은 값만 적는다.
- 문장 보충(`370689b`, 첫 실행의 점수를 보기 전, 규칙은 그대로이고 판정 코드에 맞게 문장만 보탰다): 이김과 짐의 조건이 함께 걸리면 짐이다(예: 행동에서 맞은 문항이 2개 많고 인용에서 2개 적을 때). 사전 검사는 A 다섯 번을 평가셋 v2 정답으로 세어 API로 잰 범위와 견준다. "그래프를 켠 LLM 실행을 하나도 돌리기 전에"는 "채점된 그래프 켬 LLM 실행이 하나도 없을 때"로 읽는다. 11-07(한국 시각) 첫 시도(`3bB-t1`~`t3`)는 그래프를 켜고 시작했지만 API 크레딧 부족으로 채점된 문항이 0개였다. 오프라인 검색의 그래프 켬 값(11-07, 11-12)은 이 고침 전에 이미 알려져 있었다. 오프라인 조건의 꼴(R@8 같거나 높음, MRR 0.02 안)은 원래 G1 그대로다.

### 9.4 이 측정이 보여 주지 않는 것

- 재생 데이터만 썼다. 실제 해수부와 ShipFinder 응답, 실제 배 위치 지연, 응답이 비거나 틀린 경우는 지나가지 않았다. 실제 호출은 내가 따로 정한다.
- 모델은 Haiku 5.5 하나다. 다른 모델에서 같은 값이 나오는지는 모른다.
- 문항은 42개이고 새 문항은 12개다. 한 문항이 0.0833이라 켠 길과 끈 길의 차이가 한 문항 안이면 우연과 구분하지 못한다. 이번 행동 정확도(0.9333 대 0.9333)와 인용 차(−0.0333)도 그 폭 안이다. 다섯 실행의 평균이어도 문항 수가 늘지는 않는다.
- 새 문항이 0.9667로 나온 것은 기준 0.80을 크게 넘지만, 기준 자체가 추정으로 정한 시작값이어서 눈높이가 맞았는지는 이 값으로 모른다. 틀린 것은 N10 하나(두 실행)였다.
- 판정 이름 어긋남 0은 새 문항에서만 실제로 검사한 값이다. 기대 판정이 없는 v3 화물 문항 19문장과 번호 없이 쓴 N11 7문장은 어긋남을 볼 수 없었다.
- 상한 기준은 사전 등록 그대로 넘지 못했고, 끈 길과 견준 분석은 결과를 본 뒤에 한 것이라 사전 등록 값과 같은 무게로 읽지 않는다.
- 끈 길 실행에서만 법령 검색 실패가 났다. 두 길이 같이 쓰는 단계의 우연으로 보지만 확인하지 않았다. 무효로 버린 네 번이 점수에 들어가지 않았으므로 끈 길 평균이 실제 흔들림보다 안정적으로 보일 수 있다.
- 사용자가 날짜를 실제로 어떻게 쓰는지(`11.20`, `20일` 등)는 새 문항에 든 몇 가지 꼴만 지나간다. 읽는 꼴을 늘려야 하는지는 이 측정으로 모른다.
- 수퍼바이저 길은 이번에 재지 않았다. 판정 블록과 새 도구는 에이전트 길에만 있다.
- 답 문장의 정직성은 재지 않는다. 탐지기는 등급 이름과 확신 이름이 그 화물의 판정과 같은지만 문장 단위로 보고, 풀이가 맞는지는 보지 않는다.
- 판정 자체(등급, 확신)가 실제 선박 사정에 맞는지는 이 측정이 아니다. 판정은 코드가 내고, 여기서는 모델이 그 값을 옮겨 쓰는지만 본다.
- 모델 입력 쪽 배 값 새기는 결과 파일에 입력이 없어 다시 세지 못했고 줄의 `ship_leak` 0을 믿었다. 출력 쪽(답, 초안, 질문)은 따로 세어 0이었다.
- 서버 시간대가 한국 시간이 아닐 때 끈 길의 "오늘"이 하루 어긋나는지는 배포 전 확인 항목이고 이 측정 밖이다.
