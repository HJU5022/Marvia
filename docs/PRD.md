# PRD · Converge (컨버지)

현장이 움직이는 유지보수·배포 작업의 집결 장소·시각을 정해주는 에이전트

작성: 5조 김승욱(팀장), 하정운 · 2026.09.17 · v2.1 (계획 보완 피드백 반영, 09-17 DB·로그인 결정 반영)

---

## 1. 한 줄 정의

현장이 고정되지 않은 유지보수·배포 작업에서, 현장 담당자가 업체·고객사 담당자와 집결 장소와 시각을 정하는 일을 문장 하나로 끝내고 지도 위에 그려주는 에이전트. 함정 정비 미팅(입항 일정·출입조치·업체 순회)과 SI 야간 배포 집결(배포 창·인솔·첫차 귀가·을 관례) 두 현장에서 출발한다.

---

## 2. 문제 정의

### 도메인: 현장이 움직이는 작업의 집결 조율

일반 약속과 다른 제약이 있다. 함정 정비는 입항 일정에 따라 현장(항, 부두)이 바뀌고, 업체는 전국 부대를 순회하며, 정비품 확보 같은 비정기 회의가 끼어들고, 부대 출입조치가 집결지와 시각을 가른다. SI 배포는 야간 작업 창, 고객사 출입증·보안서류·인솔 절차, 작업 종료 후 첫차 귀가, 고객사 방문 시 을이 이동하는 관례가 있다. 두 조원이 각각 6년 2개월, 4년 7개월 현장 담당자로 직접 조율했다.

### 조원의 직접 경험

| 이름 | 경험 | 기간 | 역할 | 정답을 판정할 수 있는 근거 (실제 사례) |
|---|---|---|---|---|
| 하정운 | 해군 함정 전자정비 담당으로 유지보수 업체 미팅·회의 장소 상시 조율, 긴급정비·정비품 확보 비정기 회의 주선 | 2019.12 ~ 2026.02 (6년 2개월) | 함정 정비 담당 (현장 담당자) | 인천 입항 중 레이더 고장, 서울 업체 야간 차량 출동. 도착이 30분 이상 어긋나 출입조치를 포기하고 부두 밖 집결로 전환했으나 현장·업체 모두 지리를 몰라 장소 정하고 이동하는 데 다시 30분. 긴급정비인데 조율로만 한 시간 가까이 소모 |
| 김승욱 | SI 파견 개발자로 고객사 야간 배포·운영 미팅의 집결 장소·시각 조율 (KT, LG, CJ, 공공) | 2020.10 ~ 2025.04 (4년 7개월, 미팅 월 1회·배포 2달 1회, 약 80회) | SI 배포·운영 담당 (현장 담당자) | 야간 배포는 일반 출입증으로 못 들어가 담당자가 1층에서 보안서류를 받고 인솔함. 부장님과 여의도역 합류로 잡았다가 둘 다 지하철이라 의미가 없고 부장님이 늦어 인솔이 밀림. 이후 "합류 지점은 인솔이 시작되는 1층"이 기준. 강남 고객사 담당자와 서로 상대 쪽으로 가겠다고 배려하다 왔다갔다 한 뒤로는 "을이 고객사 쪽으로 확정"이 기준 |

두 도메인은 서로 겪어보지 않았으므로 평가셋 정답은 각자 자기 도메인 문항을 판정하고, 상대 문항은 검토만 한다. 판정이 갈린 문항은 지우지 않고 기록한다.

### 반복되는 예외 상황

| # | 상황 | 현장 |
|---|---|---|
| 1 | 업체 도착이 예정보다 어긋나 출입조치 시각을 못 맞춤 | 함정 |
| 2 | 입항지·입항 시각이 바뀌어 미팅 장소와 업체 순회 동선을 다시 잡아야 함 | 함정 |
| 3 | 현장·업체 모두 그 일대 지리를 몰라 집결지 정하는 데 시간 소모 | 함정 |
| 4 | 야간 배포 출입은 인솔 기반인데 합류 지점을 역으로 잡아 한 사람 시간 낭비, 인솔 지연 | SI |
| 5 | 고객사 출입증·보안서류를 전원이 함께 작성해야 해 흩어져 가면 안 됨 | SI |
| 6 | 고객사·을 관계에서 서로 배려하다 장소 결정을 미룸 | SI |
| 7 | 야간 작업 종료 후 귀가 수단(첫차)을 따로 확인 | SI |

### 기존 대안과 한계

| 대안 | 한계 |
|---|---|
| 전화·카톡 조율 | 긴급정비에서 장소·시간 조율로만 한 시간. 결정 근거가 남지 않음 |
| 카카오맵·네이버 길찾기 | 사람 1명·장소 1개 단위. 출입조치, 인솔, 배포 창, 업체 순회를 모름 |
| 범용 LLM | 출입조치·위병소·인솔·을 관례 같은 현장 절차를 모르고 "근처 카페에서 만나세요"로 답함 |

### 문제 정의 문장

현장이 움직이는 작업의 담당자는 업체·고객사와 집결 장소·시각을 정할 때 출입조치, 입항 일정, 야간 작업 창, 인솔 절차 같은 현장 제약을 매번 사람이 계산하며 30분에서 한 시간을 쓴다. 기존 도구는 그 제약을 모른다.

## 3. 해결 범위

### 중심 질문과 부가 질문

| 구분 | 입력 예 (조원 실제 사례) | 에이전트가 정하는 것 | 결과 화면 |
|---|---|---|---|
| 중심: 집결지·시각 결정 | "인천 입항 중 레이더 고장, 업체가 밤에 차로 출동, 도착이 30분 어긋남. 어디서 만나?" | 집결지(부두 안/밖, 위병소, 고객사 1층), 전환 판정, 각자 출발 시각 | 핀 + 참석자별 경로선 + 판정 근거 |
| 부가: 장소 확정 후 시각 | "여의도 배포 건물 앞 10시, 둘 다 지하철. 각자 언제 나가?" | 각자 출발 시각, 여유, 첫차 | 핀 1개 + 참석자별 경로선 |

### 프리셋 2개 (규칙 문서를 갈아끼움)

| 프리셋 | 사용자 | 상대 | 현장 규칙이 다루는 것 |
|---|---|---|---|
| ship_maintenance | 함정 정비 담당 | 유지보수 업체 (전국 순회) | 입항 일정 변동, 접안 부두, 출입조치 소요와 위병소 집결, 도착 어긋남 시 부두 밖 전환, 업체 당일 순회 동선, 야간 단독 출동 |
| si_deploy | SI 배포·운영 담당 | 고객사, 동료 | 야간 배포 창, 출입증·보안서류·인솔 지점, 작업 종료 후 첫차 귀가, 임원 동행 시 본사 집결·법인차, 고객사 방문은 을이 이동, 장비 있는 날 주차 |

프리셋은 사용자가 고르거나 문장에서 추론하며, 같은 파이프라인에 규칙 문서(Skill) 하나만 바뀐다.

### 할 것

- 문장·카톡 캡처에서 참석자별 출발지·이동수단·시간 제약 추출
- 추출한 출발지를 지도에 참석자 핀으로 먼저 보여주고, 사용자가 핀 드래그·지도 클릭·주소 검색으로 수정할 수 있게 함 (확신도가 높으면 자동 통과)
- 집결 후보 생성(위병소·항만 입구·고객사 1층 같은 절차 시작점, 또는 랜드마크 검색) 또는 지정 장소 좌표 확정
- 참석자별 소요시간 계산: 차량은 출발 시각 기준 예측 경로, 대중교통은 환승·첫차 포함
- 출입조치·인솔·배포 창·을 관례·업체 순회 규칙으로 집결지 판정과 전환 이유 생성
- 지도 위 핀·경로선·출발 시각·근거 한 줄 표시, 공유 링크 생성
- 조건을 바꿔 다시 물으면 이전 입력을 유지한 채 재계산

### 하지 않을 것

- 출발 후 실시간 길안내·재탐색 (네비의 영역)
- 식당 예약, 영업시간 확인
- 차량 1대가 2명 이상 픽업할 때의 순서 최적화
- 출입조치 신청 자체(행정 절차)와 부대·고객사 내부 위치 안내
- 참석자별 회원 관리 (주선자·참석자 모두 구글 로그인은 하지만, 참석자 정보를 따로 관리하지는 않는다. 참석자는 공유 링크로 열람하고 본인 출발지만 직접 고친다)

### LLM이 맡는 일과 맡지 않는 일

| LLM이 맡음 | 코드·API가 맡음 |
|---|---|
| 문장·캡처 → 참석자 슬롯 JSON (소형 모델, 파인튜닝) | 주소·장소명 → 좌표 |
| 캡처 이미지 판독 (비전 모델) | 집결 후보 검색(절차 시작점·랜드마크) |
| 계산된 소요시간 표 + 현장 규칙 문서 → 집결지 판정·전환 이유·근거 문장 (대형 모델) | 경로·소요시간 산출, 절차 소요 반영 역산 |
| 재질문 시 바뀐 조건만 갱신 | 지도 렌더링, 세션 저장 |

LLM은 입구(말 이해)와 출구(판단·설명)에만 있고, 가운데 계산은 전부 결정적이다. 틀린 지점을 트레이스에서 잡기 위한 설계다.

## 4. 사용 장면과 화면

### 사용 장면 세 가지 (조원의 실제 사례)

| 장면 | 상황 | 입력 | 에이전트 판단 | 결과 |
|---|---|---|---|---|
| 1. 함정 긴급정비 출동 | 인천 입항 중 레이더 고장. 서울 업체 직원이 밤에 차로 출동, 도착이 30분 넘게 어긋남 | "도착이 30분 어긋나는데 어디서 어떻게 만나?" | ship_maintenance: 출입조치 포기 판정, 부두 밖 랜드마크 집결, 주차 표시 | 핀 1개(항만 입구), 업체 경로선, "출입조치 시각 초과로 밖 집결" 근거 |
| 2. SI 야간 배포 집결 | 여의도 고객사, 부장님 강서구·나 송파구 둘 다 지하철. 인솔 필요. 부장님이 역에서 합류하자고 함 | "여의도역에 몇 시까지 가면 돼?" | si_deploy: 합류 지점은 역이 아니라 인솔이 시작되는 1층, 인솔 시각 10~20분 전 도착, 첫차 참고 | 핀 1개(고객사 1층), 각자 경로선·출발 시각, "합류 지점 = 인솔 시작점" 근거 |
| 3. 입항지 변경 | 목요일 인천 미팅이 평택 입항으로 바뀜. 업체는 오전 대전 방문 후 이동 | "어떻게 다시 잡아?" | ship_maintenance: 평택 기준 재계산, 업체 순회 동선 반영, 입항 시각 미확정이면 잠정, 출입조치 재신청 경고 | 핀 이동, 업체 경로선(대전 → 평택), "잠정" 표시 |

세 장면 모두 출발 전에 결정을 내리는 순간에 쓰고, 정한 뒤 이동은 각자 네비로 한다. 프리셋 하나 차이로 파이프라인은 하나다.

### 사용 순서

```
[사용자]
  1. 브라우저로 사이트 접속, 구글 로그인 (앱 설치 없음. 공유 링크는 사이트 주소 그대로이고, 링크를 여는 참석자도 로그인)
  2. 화면: 왼쪽 지도, 오른쪽 채팅창 + 이미지 업로드 버튼
  3. 문장 입력 또는 카톡 캡처 업로드
  3-1. 지도에 참석자 핀이 먼저 찍힘. 위치가 틀리면 핀을 끌거나 지도를 클릭해 수정, 맞으면 계산
  4. "경로 계산 중 → 판정 중" 진행 표시 (5~10초)
  5. 지도에 후보 핀 + 참석자별 경로선, 옆 표에 이름·이동수단·소요시간·출발 시각·근거
  6. 조건 변경 재질문 ("업체 도착이 1시간 늦는대") → 재계산
  7. 후보 선택 → 공유 링크 복사 → 카톡에 공유
  8. 당일 이동은 각자 네비 (서비스 범위 밖)
```

화면 구성 (와이어프레임)

```
+--------------------------------------------------+------------------------------+
|                                                  |  채팅                         |
|   [카카오맵]                                      |  > 여의도 배포, 부장님 강서구  |
|                                                  |    나 송파구, 인솔 필요 ...    |
|      ● 고객사 1층 (집결)                          |  < 합류 지점은 여의도역이     |
|     /   \                                         |    아니라 인솔이 시작되는     |
|  부장님   나                                      |    고객사 1층입니다.          |
| (지하철) (지하철)                                 |  [참석자 표]                  |
|                                                  |  부장님 지하철 50분 21:00 출발 |
|                                                  |  나 지하철 40분 21:10 출발    |
|                                                  |  귀가 첫차 05:30 참고         |
|                                                  |                              |
|                                                  |  [입력창] [이미지] [공유 링크] |
+--------------------------------------------------+------------------------------+
```

실패 화면: 필수 정보(도착 시각, 출입조치 여부, 이동수단)가 빠지면 판정 없이 "업체 도착 예정 시각과 출입조치 신청 여부를 알려주세요"처럼 되묻는다. API 장애 시 "경로 조회 실패, 잠시 후 재시도" 안내와 재시도 버튼.

## 5. 아키텍처

```
사용자 → Vercel / Next.js (지도 + 채팅 UI)
       → Cloud Run / FastAPI
            POST /api/agent   : 에이전트 실행 (Pydantic 출력 계약, 검증·재시도)
            GET  /health      : 헬스체크
            /mcp              : Streamable HTTP MCP endpoint (토큰 인증)
            ├─ 소형 모델 (GGUF, CPU, llama.cpp)      : 슬롯 추출
            ├─ OpenRouter (Sonnet 5 / Gemini Flash) : 판정·근거, 캡처 판독
            ├─ MCP 도구 → 카카오 로컬, 카카오모빌리티, TMAP 대중교통
            ├─ Supabase Postgres                    : 세션, 요청 로그, 경로 캐시, 피드백
            └─ Langfuse Cloud                       : 트레이스, 프롬프트 버전, 평가셋
```

에이전트 내부 파이프라인

```
입력(문장/캡처) → [슬롯 추출: 소형] → [지오코딩: MCP, 기준 좌표 편향] → [참석자 핀 확인: 사용자] → [후보 생성: MCP]
  → [소요시간: 차량 MCP / 대중교통 MCP, 집결지 있으면 2구간] → [규칙 판정·근거: 대형 + Skill]
  → [출력 계약 검증: Pydantic, 실패 시 재시도 1회 → 후보 핀만 폴백] → 지도 화면
```

브라우저는 Cloud Run을 직접 부르지 않고 Next.js API 라우트를 거친다. 카카오·OpenRouter 키가 브라우저에 나가지 않고, /api/agent와 /mcp의 역할이 분리된다.

LLM 호출과 외부 API 호출은 각각 services/ 한 곳에 모아 3차에서 교체 가능하게 둔다.

### Skill과 MCP 서버

```
skills/converge/
  SKILL.md        판단 순서 (절차 소요 → 집결지 판정 → 역산 → 전환 조건)
  rules/
    access.md     출입조치·인솔: 절차 소요를 먼저 빼고 역산, 합류 지점은 절차 시작점(위병소·1층), 도착이 기준 이상 어긋나면 부두 밖 전환
    schedule.md   입항 일정·배포 창: 미확정이면 잠정, 변경 시 업체 순회 동선과 출입조치 재계산, 야간 종료 후 첫차
    convention.md 을 관례·임원 동행: 고객사 방문은 고객사 쪽 확정, 전원 동행 미팅은 본사 집결 후 법인차, 서로 배려 시 상대 쪽 확정
    transport.md  여유·정체: 고객사 미팅 여유 20분, 환승 10분 가산, 장비 있는 날 차량·주차
    vendor.md     업체 순회: 당일 다른 방문지 반영, 야간 단독 출동은 차량 전제·주차 확인, 지리 모르면 랜드마크 고정
  presets/        ship_maintenance · si_deploy (요청에 따라 하나만 프롬프트에 포함)
  failures.md     되묻기(도착 시각·출입조치·이동수단)·전환·범위 밖 조건

규칙값은 두 조원의 현장 경험에서 정했고, 각 파일 첫 줄에 근거 사례를 적는다. 상식 수준 규칙(공평성, 막차 등)은 두지 않는다.

mcp_server/       geocode(기준 좌표 편향) · search_places · route_car · route_transit · first_last_train · departure_calc
                  카카오 로컬(일 10만 건), 카카오모빌리티 자동차·미래 운행(일 10,000·5,000건), TMAP 대중교통(종량제 건당 0.88원), 지하철 첫차·막차 공공데이터
                  참석자마다 개별 호출 후 캐시. 다중 출발지 API는 반경 10km 상한과 경로 좌표 부재로 쓰지 않음
                  /mcp 토큰 인증, 키는 서버에만
```

## 6. LLM 제어 설계

### 출력 계약 (Pydantic, 상세는 SDD 3·4절)

두 계약으로 나눈다. LLM이 만드는 건 이 둘의 일부뿐이고 숫자는 코드가 넣는다.

```
Slots (계약 1, 슬롯 추출 결과)
  preset: ship_maintenance | si_deploy
  access: {required: bool, applied: bool, lead_min} 출입조치·인솔 정보
  schedule_confirmed: 입항·배포 시각 확정 여부
  datetime, purpose, destination
  participants[]: name, origin, transport(car|transit|walk|null), pickup, unfamiliar
  rendezvous: {name, transport_after} 또는 null
  constraints[], missing[], out_of_scope

Result (계약 2, 최종 결과)
  candidates[]: name, coord, rank, max_duration_min, fairness_score, parking, reason, rejected_reason
  per_participant[]: transport, duration_min, buffer_min, departure_time, transfer_count, first_train, last_train, polyline, via_rendezvous
  rendezvous_departure, confidence, model_small, model_large, prompt_version, routed_to

AgentResponse (API 응답)
  session_id, stage(need_confirm | need_info | done | out_of_scope | failed), slots, result, questions[], message, trace_id
```

### 실패 경로

| 실패 유형 | 처리 |
|---|---|
| 슬롯 JSON 스키마 위반 | 재요청 1회 → 실패 시 대형 모델로 승격 → 그래도 실패 시 되묻기 |
| 한자·가나 등 비허용 문자 | 계약 위반으로 처리, 재시도 |
| 이동수단 미지정 | 추측하지 않고 되묻기. 문맥 추론 시 확인 단계에 표시 |
| 도착 시각·출입조치 여부 누락 | 집결지를 정하지 않고 되묻기 |
| 업체 도착이 기준 이상 어긋남 | 출입조치 포기, 부두 밖 랜드마크 집결로 전환 판정 |
| 입항·배포 시각 미확정 | 결과를 잠정으로 표시, 확정 시 재계산 |
| 출발 후 실시간 상황 요청 | 범위 밖 안내, 통화·네비 권유 |
| 출발지 지명이 여러 지역에 해당 (예: 서면 → 부산·순천) | 기준 좌표 편향으로 1차 해소, 그래도 확신도 낮으면 참석자 핀 확인 단계에서 사용자가 수정 |
| 장소명 모호 | 지역검색 후보 3개 핀으로 되묻기 |
| 경로 API 타임아웃·5xx | 백오프 재시도 2회 → 실패 참석자만 "조회 실패" 표시, 나머지로 판정 |
| 대중교통 API 장애 | 가장 가까운 지하철역 도보 거리로 근사, 근사임을 표시 |
| 요청당 비용 상한 초과 | 차단, 안내 |
| 유해·무관 입력 | 거부 응답 |
| 90분 초과 참석자 | 후보 탈락, 이유 표시 |

### 모델 선택과 비교 계획

| 자리 | 후보 | 비교 기준 |
|---|---|---|
| 슬롯 추출 (소형) | Qwen3 0.6B 파인튜닝 / HyperCLOVA X SEED 1.5B 파인튜닝 / Qwen3 1.7B 파인튜닝 / 학습 전 베이스 / Sonnet 5 | 슬롯 정확도, 계약 준수율, 언어 섞임, p95, 비용 |
| 판정·근거 (대형) | Sonnet 5 / Gemini 3.8 Flash / GPT-5.6 Luna | 순위 정확도, 근거 적절성(judge), p95, 비용 |
| 캡처 판독 | Gemini 3.8 Flash / 대안 1개 | 참석자 추출 정확도 |

같은 평가셋, 같은 프롬프트, 온도 0으로 비교한다.

### 라우팅

인원 2명 이하, 장소 확정, 절차(출입조치·인솔) 없음, 집결지 없음이면 소형 모델(슬롯 추출)과 코드(역산)만으로 처리하고 대형 모델을 부르지 않는다. 하나라도 해당하지 않으면 대형 모델이 판정한다. 소형 모델은 어느 경우든 슬롯 추출만 담당한다. 라우팅 전후 요청당 비용을 측정해 절감률을 제시한다.

### 프롬프트 관리

모든 프롬프트는 Langfuse Prompt로 버전 관리. 트레이스에 프롬프트 버전이 연결된다.

## 7. 관측과 평가

- Observability: 모든 LLM·API 호출 트레이스, user_id·session_id, 재시도 표시, 요청 ID·모델·토큰·지연 구조화 로그
- Prompt Management: Langfuse Prompt v1/v2, 배포 없이 교체·롤백 시연
- Evaluation: 평가셋 30건(정상 9·경계 12·실패 유도 9)을 Langfuse Dataset으로. 계획 보완서의 10문항이 시작점이며, 경계 문항은 함정·SI 현장에서 조원이 직접 겪은 상황으로만 만들고 정답은 그 현장을 겪은 조원이 정한다. 입력과 정답을 LLM으로 만들지 않는다. 평가 축은 슬롯 정확도·도구 선택 정확도·규칙 판정 정확도(코드)·현장 적합성(사람, 필요 시 LLM-as-judge 보조)·계약 준수율. LLM-as-judge는 생성 모델과 다른 회사 모델. 두 사람이 각자 판정한 뒤 갈린 문항은 기록으로 남긴다. 한 번에 하나씩 바꾸고 재측정, KEEP/DISCARD를 EVAL_REPORT.md에 기록
- 경로 API는 호출 시각에 따라 소요시간이 변하므로 절댓값이 아닌 후보 순위·규칙 적용 여부로 평가하고 변동 폭을 기록한다
- 게이트: 스키마 통과율 95% 이상, p95 15초 이하(콜드 스타트 제외), 유해 입력 오작동 0건, 요청당 비용 상한, 개인 위치 정보 유출 0건

## 9. 실현 가능성 확인 (스파이크 결과, 2026-09-15)

제품 코드를 쓰기 전에 외부 의존성을 실제 호출로 확인했다 (1~5는 스파이크 실행, 6~7은 문서 확인). 응답 원문은 spike/samples/에 보관한다.

| # | 항목 | 결과 | 근거 | 설계 반영 |
|---|---|---|---|---|
| 1 | 카카오 로컬 (지명 → 좌표, 반경 음식점) | 조건부 | HTTP 200. 필터 없이 "서면" 검색 시 순천 서면이 먼저 나옴. 지하철역 필터와 역 이름 우선 규칙으로 세 곳 모두 정확 | 지오코딩에 기준 좌표 편향 추가, 참석자 핀 확인 단계 신설 |
